## 🧭 Overview

This session is part of an ongoing series on **RAG Evaluation**. Over the last 5-6 sessions, a complete **RAG Evaluation Suite** has been built, covering **14 different metrics** across **3 levels**:

> **Component Level → Pipeline Level → Application Level**

This session's topic: **Regression Testing** — how to run the *entire* eval suite with a **single script**, generate a **summary**, and automatically detect whether recent changes improved or *silently broke* your RAG application.

### Prerequisites
- Understanding of RAG (Retrieval Augmented Generation) architecture
- Familiarity with RAG evaluation metrics: Faithfulness, Answer Relevancy, Contextual Relevancy, Precision, Recall, Toxicity, PII Leakage, Scope Adherence, Latency, Cost, Reliability
- Basic Python (functions, JSON handling, file I/O)
- Concept of "LLM-as-a-judge" evaluation

### Why It Matters
Without regression testing, you can **silently break** your AI application while trying to fix one thing. Example: you improve **Recall** by tuning `k` and adding a reranker — but Precision, Contextual Relevancy, or Latency might quietly degrade, and you'd never know until it's in production causing real damage. Regression testing acts as a **safety net** before every deployment.

## 🔁 Recap – RAG Eval Suite Journey So Far

> **Definition:** A RAG Evaluation Suite is a collection of evals used to measure the health/quality of a RAG application at multiple levels.

The suite is organized into **3 categories**:

<a name="what-is-regression"></a>
## 🧩 What is Regression Testing?

> **Regression** (English meaning): *Returning to a previous, less advanced, or worse state.*

If your system moves to a **worse state** compared to before, that's called **regression**. Testing for this is **Regression Testing**.

### 🧪 Worked Example

Imagine you built a RAG app and it's working fine, but you notice **Recall is low**. Common fixes:
- Increase the value of `k` (retrieve more chunks)
- Add a **reranker**

You apply both changes → **Recall improves from 85% → 90%** 🎉

**But here's the catch:** You were *only* watching Recall. Meanwhile:
- **Precision** might have taken a hit
- **Contextual Relevancy** might have dropped
- **Latency** might have increased (because of the reranker)

You deploy the "improved" system, only to discover **later** that other important aspects silently regressed. This is exactly the failure regression testing prevents.

> **Golden Rule:** Whenever you change anything in your system, you must verify that **ALL** aspects still perform at least as well as before — not just the one you were targeting.

<a name="traditional-software"></a>
## 💻 Regression Testing in Traditional Software

Regression testing is **not new** or LLM-specific — it's a decades-old software engineering concept.

**Example:** You migrate your API from Flask → FastAPI (v1 → v2). After deployment, you test whether overall performance is still as good as before, or worse.

This same principle **applies directly** to LLM/RAG-based application development — which is why every AI engineer must understand it.

---

<a name="why-matters"></a>
## ❓ Why Regression Testing Matters for RAG/LLM Apps

- LLM apps have **many interacting metrics** (14 in our suite) — optimizing one can silently hurt others
- Real-world business impact: a "silent AI failure" (e.g., PII leakage suddenly increasing) can cause compliance/legal issues
- Without a **systematic comparison process**, teams rely on gut-feel — risky at scale
- Enables **confident, safe iteration** — you can experiment (change `k`, chunk size, model, prompt) and know objectively if it's safe to ship

## ⚙️ The Regression Testing Workflow (Step-by-Step)

### 📌 High-Level Flow (ASCII Diagram)

```
        ┌─────────────────┐
        │   run_eval.py   │  (runs Quality + Safety + Ops evals)
        └────────┬────────┘
                 │
     ┌───────────┴────────────┐
     │                        │
  First Run               Later Run (after changes)
     │                        │
     ▼                        ▼
baseline.json           candidate.json
     │                        │
     └──────────┬─────────────┘
                ▼
          compare.py
    (uses metric_registry.json)
                │
                ▼
        Delta per metric
     (Negative delta beyond
      noise threshold = REGRESSION)
```

### Step 1: Build the Orchestrator Script (`run_eval.py`)
A single Python script that calls all other eval scripts (Quality, Safety, Ops) **in sequence** and collects results — instead of manually running each `.py` file one by one.

### Step 2: Run It the First Time → Save as `baseline.json`
This captured result becomes your **baseline** — the "before" state you'll compare all future runs against.

### Step 3: Make Your Changes
Examples of changes:
- Increase/decrease `k`
- Change chunk size
- Swap the LLM model
- Modify the system prompt
- Add/remove a reranker

### Step 4: Re-run the Script → Save as `candidate.json`
This captures the "after" state with the new configuration.

### Step 5: Compare (`compare.py`)
Takes `baseline.json` and `candidate.json
