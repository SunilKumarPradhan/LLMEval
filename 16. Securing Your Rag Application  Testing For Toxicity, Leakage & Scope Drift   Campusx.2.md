## 🛡️ Recap: Types of Guardrails {#recap-guardrails}

> **Guardrail**: Ek protective mechanism/check jo LLM application ke input ya output par lagaya jata hai taaki koi harmful, unsafe, ya out-of-scope behavior na ho.

Pehle discuss kiye gaye guardrails (input/output guardrails) ke aage, yahan 3 aur important types cover hue:

### 1️⃣ Tool Guardrails

- Jab aapka LLM/agent kisi **tool ko call** karta hai (e.g., refund API, email sender, booking system), toh tool call hone se **pehle** uske arguments ko filter/validate karo.
- **Flow**: `LLM decides to call tool → Arguments checked/filtered → Tool executed (only if safe)`
- **Example**: Agar LLM ne "refund_amount = 100000" jaisa suspicious argument bhej diya, toh tool guardrail us call ko block/flag karega before it hits the actual banking system.

### 2️⃣ Human-in-the-Loop Guardrails

- Kuch situations itni **critical/tricky** hoti hain ki poora decision AI par nahi chhodna chahiye.
- **Example**: Refund processing — agar koi attacker bank system mein ghus kar refund करवा leta hai, toh yeh bahut risky hai.
- **Solution**: Aise critical junctures par LLM/agent se power hata kar ek **human ko decision point pe rakh do**. Human ka judgment final action allow/deny karega.
- **When to use**: High-stakes actions (payments, data deletion, legal commitments) jahan galti costly ho sakti hai.

### 3️⃣ Operational Guardrails

Yeh system-level limits hote hain jo abuse/misuse ko control karte hain:

| Operational Control | Kya Roकता Hai |
|---|---|
| **Rate Limit** | Ek IP/user se bahut zyada requests aana (DoS-type attack) |
| **Token Limit** | Bahut bade prompts bhej kar resource exhaust karna |
| **Timeout** | Agent ka infinitely चलते रहना |
| **Max Agent Steps** | Agent ko infinite loop mein manipulate karke ghumaana (e.g., "10 se zyada retries allowed nahi") |

> **Real-world use case**: Agar koi attacker Denial-of-Service (DoS) attack karta hai bahut saare bade-bade prompts bhej kar, toh operational guardrails (jaise per-MAC-address token transaction limit) usse rok sakte hain.

**Nutshell Framework**:
```
Build LLM Application → Evaluate (Test for safety) → Find Weak Points → Fix with Guardrails
```

## 🔴 Red Teaming {#red-teaming}

> **Red Teaming**: Evaluation ka hi ek part hai, jahan aapki hi team ke kuch members "attacker" ka role play karte hain, taaki naye tareeke dhoonde ja sakein jinse system ko attack kiya ja sakta hai.

### Kyun Zaroori Hai?
- Humein already kuch known attack methods pata hain (jailbreaks, prompt injection, etc.), lekin yeh **saare possible tareeke nahi** hain.
- Naye failure modes samay ke saath discover hote rehte hain.
- Red teamers ka exact job: **"Ab tak jo hume pata hai uske alawa aur kya-kya tareeke hain jisse system attack ho sakta hai?"**

### Analogy: Ethical Hacking / Penetration Testing
Cybersecurity mein "Ethical Hackers" / "Penetration Testers" hote hain jo apni hi company ke products ko attack karke vulnerabilities dhoondte hain. Red Teaming bilkul yehi concept hai, lekin AI systems ke liye.

### Ongoing Loop

```
┌─────────────────────────────────────────┐
│  Current Failure Modes → Evaluate        │
│         ↓                                │
│   Apply Guardrails                       │
│         ↓                                │
│  Red Teaming discovers New Failure Modes │
│         ↓                                │
│   Evaluate New Failure Modes             │
│         ↓                                │
│   Apply New Guardrails                   │
│         ↓ (repeat forever)               │
└─────────────────────────────────────────┘
```

Yeh cycle kabhi khatam nahi hota — jaise cybersecurity ek continuously evolving field hai, waise hi **AI Safety & Security** bhi evolve ho rahi hai.
