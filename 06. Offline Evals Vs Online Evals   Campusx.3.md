## 🎯 Overview {#overview}

This is **Part 3** of a 3-part lecture on Offline vs Online Evaluations for LLM-based applications (like chatbots/RAG systems). This part focuses primarily on:

- Completing the discussion on **online evaluation pipelines**
- Explaining how to monitor **computed quantities** (like hallucination) in production, which is more complex than monitoring simple **captured quantities** (like latency)
- Introducing **LLM-as-a-Judge** as an evaluator
- Discussing **cost problems** and how **sampling** (especially **stratified sampling**) solves them
- A live walkthrough of **LangSmith** as an evaluation platform
- Explaining the **self-improving loop** that connects online production failures back to offline datasets

> **Prerequisites**: You should already know the difference between offline and offline evaluations, what "captured" vs "computed" quantities mean, and basic concepts of reference-based vs reference-free evaluation (covered in earlier parts of this series).

**Why this matters**: Once you deploy an LLM application (chatbot, RAG system, agent) to production, you can't just "set it and forget it." You need continuous monitoring to know if things like hallucination, toxicity, or bias are creeping in — this is what separates a hobby project from a production-grade, scalable AI system serving thousands/millions of users.

## 🔁 Recap: Captured vs Computed Quantities {#recap}

> **Captured Quantity**: A metric you can directly record/log without any computation — e.g., latency, token count, cost, user feedback (thumbs up/down).

> **Computed Quantity**: A metric that requires some evaluation logic/model to calculate — e.g., hallucination rate, toxicity score, faithfulness, correctness.

This distinction matters because the **monitoring pipeline is different** for each type — captured quantities need no evaluator, while computed quantities need an evaluator (often another LLM).

## 📊 Online Eval Pipeline for Captured Quantities {#captured-flow}

For something simple like **latency**, the flow is:

```
[Chatbot Conversation] 
       ↓
[Tracing/Logging Tool - e.g., LangSmith] 
       ↓ (record raw value directly, e.g., 2.03 sec)
[Dashboard - shows metric over time]
       ↓
[Alerting System - triggers if threshold crossed]
```

### How Alerting Works (in LangSmith-like tools)
- You **select a project**
- Give the **alert a name**
- Choose **which metric** to alert on
- Set condition: *"Alert when feedback metric X exceeds threshold Y in last N minutes"*
- Choose **notification channel**: Slack, PagerDuty, or your **own custom API**

> No evaluator is needed here because the quantity (latency) is directly observable — there's nothing to "judge" or "compute."

## 🧠 Online Eval Pipeline for Computed Quantities (Main Topic) {#computed-flow}

This is the **most important and interesting part** of the lecture — tracking a **computed quantity** like hallucination in real-time production.

### The Problem Statement
> We want to check in real-time: **"Is our chatbot hallucinating?"** — This needs to be tested directly in production, not just offline.

### The Pipeline

```
[500 conversations/day] 
       ↓
[Step 1: Log everything] (using a tool like LangSmith)
       ↓
[Step 2: Sampling] (select subset, e.g., 100 out of 500)
       ↓
[Step 3: Set up an Evaluator] (LLM-as-a-Judge, reference-free)
       ↓
[Evaluator computes metric] → e.g., Hallucination Rate
       ↓
[Send metric to Dashboard] (aggregated over time)
       ↓
[Alerting System] (trigger if threshold crossed)
```

This is structurally similar to the captured-quantity flow, **but with two new additions**:
1. **Sampling** step (to control cost)
2. **Evaluation** step (to actually compute the metric using an LLM)

## 🔍 Deep Dive: Hallucination Detection Example {#hallucination}

Let's say your chatbot handles **500 conversations/day**, and you want to check if it's hallucinating.

### Step-by-Step:

1. **Log every conversation** using a tracing tool like LangSmith.
2. **Set up an evaluator** — since hallucination checking has no fixed "correct answer," this becomes a **reference-free evaluation**.
3. Use an **LLM-as-a-Judge**:
   - Feed it the **retrieved context** (from RAG)
   - Feed it the **user's question**
   - Feed it the **chatbot's generated answer**
   - Provide a **detailed rubric** guiding the judge on how to detect hallucination
   - Ask: *"Is this hallucinating or not?"*

## ⚖️ Reference-Based vs Reference-Free Evaluation {#ref-based-free}

> **Reference-Based Evaluation**: You have a **golden dataset** with correct answers (an "answer key") to compare against. Example: UPSC exam-style evaluation where correct answers are known.

> **Reference-Free Evaluation**: There is **no golden dataset** or correct answer key available. You must judge quality without ground truth — like checking hallucination, where there's no pre-defined "correct" answer for every possible user query.

### Decision Guide

| Situation | Evaluation Type | Example |
|---|---|---|
| You have correct answers to compare against | Reference-Based | Factual QA with known answers |
| No correct answer exists, judging quality/behavior | Reference-Free | Hallucination, toxicity, tone |

## 🤖 LLM-as-a-Judge {#llm-judge}

> **Definition**: Using a (usually more powerful) LLM to evaluate the output of another LLM based on a given rubric, context, and question — used when no ground truth exists (reference-free evaluation).

### How it works:
1. Take a **powerful LLM** (the "judge")
2. Provide it:
   - The **retrieved context**
   - The **user's question**
   - The **chatbot's generated output**
   - A **detailed rubric** (instructions on how to judge hallucination, correctness, etc.)
3. The judge LLM outputs a verdict (e.g., "hallucinating" / "not hallucinating") based on the rubric

### Why is this needed?
Because for computed, subjective, or open-ended quality metrics (hallucination, bias, toxicity), there's no simple formula — you need judgment, and an LLM can approximate human judgment at scale.

## 💰 The Cost Problem & Sampling {#sampling}

### The Big Problem
> **Can we run the LLM-as-a-Judge evaluator on ALL 500 conversations?**

**Answer: No — it would be extremely costly.**

- You're already paying for the LLM to generate 500 chatbot responses
- Now you'd ALSO pay for an LLM to evaluate all 500 responses
- This can **more than double your costs**

### The Solution: Sampling
> **Sampling**: Instead of evaluating every single conversation, you randomly (or strategically) select a **subset** of conversations to run your evaluator on.

Example: Out of 500 conversations/day, randomly select **100 conversations** and run the hallucination evaluator only on those.

The resulting metric (hallucination rate) is then:
- Sent to the **dashboard**
- Aggregated over time
- Used to **trigger alerts** if it crosses a threshold

## 🎯 Random Sampling vs Stratified Sampling {#stratified}

### Question Raised in Class
> Is **random sampling** the best strategy, or is there something better?

### Problems with Pure Random Sampling
Not all conversations are equally likely to contain a problem. For example:
- Conversations with a **👍 thumbs up** → likely fine, low priority to check
- Conversations with a **👎 thumbs down** → high priority, likely have issues
- Conversations that **ended abruptly**
- Conversations with **escalations**
- Conversations where the **user repeated/rephrased the same question** multiple times
- Conversations involving **sensitive topics**: money, refunds, admissions, fees

### The Better Solution: Stratified Sampling

> **Stratified Sampling**: Dividing your data into categories (strata) first, then sampling **more heavily from problematic/high-risk categories** and less from "normal" ones.

### How to Implement:
1. **Categorize** all conversations (e.g., using a small classifier model) into buckets like:
   - Thumbs down conversations
   - Money/refund-related conversations
   - Abruptly ended conversations
   - Escalated conversations
2. **Sample more** from risky/problematic categories
3. **Sample less** from normal/safe categories

> This is essentially a form of **clustering** — you need a small auxiliary model to detect which category a conversation belongs to (e.g., detecting thumbs-down, detecting topic like "refund").

### Why Stratified Sampling is Better

| Sampling Type | Pros | Cons |
|---|---|---|
| Random Sampling | Simple, unbiased | May miss rare but critical failure cases |
| Stratified Sampling | Higher chance of catching real hallucinations/issues | Requires extra classification step (small model) |
