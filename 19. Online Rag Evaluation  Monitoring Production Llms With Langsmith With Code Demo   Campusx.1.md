## 📘 Overview

This is the **final session in the RAG Evals series**. Till now, the course covered:

1. **Offline Evaluation** — Building an eval suite with ~14–15 metrics (Retriever, Generator, Pipeline, Application, Safety, Operational levels) and testing the application *before* deployment.
2. **Regression Testing** — Ensuring that changing one component doesn't break the whole system.

Today's topic: **Online Evaluation** — what happens *after* your application is deployed and real users start interacting with it.

> **Definition:** Online Evaluation is the continuous process of evaluating, observing, and monitoring an LLM-based application *after* it has gone live, ensuring it doesn't silently degrade in production.

### Why This Matters
- Deployment is NOT the finish line — it's a new evaluation phase.
- Companies that deploy chatbots/LLM apps must **continuously** track quality, safety, and performance.
- This is done using **observability + monitoring + evaluation tools** like **LangSmith** or **LangFuse**.

### Prerequisites
- Understanding of the offline RAG eval suite (Contextual Recall/Precision, Faithfulness, Answer Relevancy, Correctness, Completeness, Style, Scope, Leakage, Toxicity, Latency, Cost, Reliability)

## ⚖️ Offline vs Online Evaluation

| Aspect | Offline Evaluation | Online Evaluation |
|---|---|---|
| When | Before deployment | After deployment (production) |
| Data | Golden dataset (with correct/reference answers) | Real user queries (no reference answers) |
| Reference Answer Available? | ✅ Yes | ❌ No |
| Purpose | Validate + prevent regression | Continuously monitor live health |
| Metrics possible | All (reference-based + reference-free) | Only **reference-free** metrics |

> **Core Insight:** In offline eval, we build a golden dataset that includes the "correct answer" for every question, enabling reference-based metrics. In online eval, users ask **completely new, unseen questions** — we have no way of knowing the "correct" answer in advance. Hence, **any metric requiring a reference/ground truth cannot be computed online.**

## 🔍 Which Metrics Survive Online?

The instructor revisited all metrics from the offline suite and classified each as **Reference-Based (needs correct answer)** or **Reference-Free (no correct answer needed)**.

### Classification Table

| Level | Metric | Needs Reference? | Usable Online? |
|---|---|---|---|
| Retriever | Contextual Recall | ✅ Yes | ❌ No |
| Retriever | Contextual Precision | ✅ Yes | ❌ No |
| Generator | Faithfulness | ❌ No | ✅ Yes |
| Generator | Answer Relevancy | ❌ No | ✅ Yes |
| RAG Pipeline | Contextual Relevancy | ❌ No | ✅ Yes |
| RAG Pipeline | Faithfulness | ❌ No | ✅ Yes |
| RAG Pipeline | Answer Relevancy | ❌ No | ✅ Yes |
| Application | Correctness | ✅ Yes | ❌ No |
| Application | Completeness | ✅ Yes | ❌ No |
| Application | Style | ❌ No | ✅ Yes (but skipped, see below) |
| Safety | Scope | ❌ No | ✅ Yes |
| Safety | Leakage | ❌ No | ✅ Yes |
| Safety | Toxicity | ❌ No | ✅ Yes |
| Operational | Latency | N/A (logged, not "measured") | ✅ Yes |
| Operational | Cost | N/A (logged) | ✅ Yes |
| Operational | Reliability | N/A (logged) | ✅ Yes (needs Grafana/Prometheus — out of scope) |

> **Rule of Thumb:** Metrics like Correctness, Completeness, Contextual Recall, and Contextual Precision are **reference-based** — they need a "golden/correct answer" to compare against. Since online users ask unpredictable, novel questions, there's no golden answer available, so these metrics simply **cannot be computed in production**.

## 🎯 Building the Online Eval Suite

Given time constraints, the instructor picked a **practical subset (6 metrics)** to demonstrate, out of everything that's theoretically possible:

### Final Online Eval Suite (What Will Actually Be Built)

| Category | Metrics Chosen | Reason |
|---|---|---|
| **Quality** (RAG Triad) | Contextual Relevancy, Faithfulness, Answer Relevancy | Reference-free, catches hallucination/relevance drift |
| **Safety** | Toxicity (only, out of Scope/Leakage/Toxicity) | Time constraint — rest can be done similarly |
| **Operational** | Latency, Cost | Automatically captured once tracing is set up |

### What Was Deliberately Skipped and Why

- **Style** → Skipped because:
  1. Time constraints in a 2-hour session.
  2. Style scores are **stable** — they don't fluctuate drastically once deployed (if offline style score ≈ 80, it won't suddenly crash to 30 online).
- **Scope & Leakage** → Same category as Toxicity (safety); skipped for time but can be done the same way.
- **Reliability** → Needs external tools like **Grafana** and **Prometheus**; beyond this lecture's scope.
- **Component-level Generator eval** → Simplified by just using the **RAG Triad** (3 pipeline-level metrics) instead of separate generator-level metrics.

### Execution Strategy (Order of Implementation)

```
1. Operational metrics first (Latency, Cost)  → Easiest — automatic via tracing
2. Safety metric (Toxicity)                    → Manual setup required
3. Quality metrics (RAG Triad)                 → Manual setup required
4. Custom Dashboard                            → Visualize everything
5. Alerts                                      → Notify on threshold breach (e.g., Slack)
```

> **Why Operational Metrics First?** Once you connect your app to LangSmith and traces start logging, **latency and cost are captured automatically** — zero extra code needed. This makes it the easiest starting point.

## 🛠️ Step-by-Step LangSmith Setup

### Step 1: Create a LangSmith Account & Project

1. Go to **smith.langchain.com**
2. Sign in (e.g., via Google login)
3. Navigate to the **Tracing** tab
4. If no project exists, click **"+ New Application"**
5. Name it (e.g., `CX Doubt Solver` — avoid special characters/naming conflicts)
6. Click **Create Application**

This creates a **project view** inside LangSmith where all traces for this application will be logged.

### Step 2: Generate API Key & Configure `.env`

1. Inside the project, click the button to **generate an API key**
2. Copy the key
3. Open your project's `.env` file and add:

```bash
# .env file

OPENAI_API_KEY=your-openai-key-here     # already existed

# New LangSmith config added:
LANGSMITH_TRACING=true
LANGSMITH_ENDPOINT=https://api.smith.langchain.com
LANGSMITH_API_KEY=your-generated-langsmith-api-key
LANGSMITH_PROJECT=CX Doubt Solver
```

> Note: The Anthropic API key (if present) can be removed if not used.

### Step 3: Install LangSmith SDK

```bash
uv add langsmith
```

> This adds the LangSmith Python package as a dependency using the `uv` package manager. (If using pip: `pip install langsmith`)

**That's it** — no code changes needed yet. Your app is now connected to LangSmith purely via environment variables.

## 🔗 Tracing Your RAG Pipeline

### Running the Pipeline for the First Time

```bash
python -m src.rag_pipeline
```

- This runs `rag_pipeline.py` with a hardcoded question (e.g., "What is GSM8K?")
- Behind the scenes: question → context retrieval → answer generation
- LangSmith **automatically captures this as a trace** — no manual logging code required

### What Gets Captured Automatically

Once you check the **Tracing** tab in LangSmith, clicking on the trace reveals:

- The input question
- The output answer
- The context used
- **Latency** (e.g., 4.14 seconds)
- **Cost** (e.g., $0.0004)

> **Key Insight:** Simply by connecting env variables, LangSmith passively captures Latency and Cost for every pipeline run — this is the "free" part of online monitoring.

## 🩹 Fixing Incomplete Traces with `@traceable`

### The Problem Discovered

When inspecting the trace in detail, the instructor noticed something crucial: the trace only showed:

```
Prompt Template → Chat OpenAI (LLM call) → String Output Parser
```

**Missing: The Retrieval step!** Even though the RAG pipeline uses a vector database + reranker to fetch relevant chunks, this entire retrieval process was **not being traced** by default.

> **Why this matters:** If retrieval isn't traced, your latency number is *wrong* (too low) — it doesn't account for the time taken to search the vector DB and rerank results. This gives a false sense of system performance.
