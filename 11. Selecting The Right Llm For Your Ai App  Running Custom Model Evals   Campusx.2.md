## 💰 Prompt Caching — Saving Money on Repetitive Prompts {#prompt-caching}

> **Definition**: Prompt Caching is a cost-optimization technique offered by LLM providers where a **repeated portion of your prompt** (e.g., system instructions, schema description) is stored ("cached") on the provider's servers, so you don't pay full price for that portion on every subsequent call.

### Why does this exist?

In many real applications (like our Text-to-SQL bot), the prompt sent to the LLM has **two parts**:

```
[STATIC PART: system instructions + database schema] --- SAME for all 50,000 queries
[DYNAMIC PART: user's actual question]                --- CHANGES every query
```

Without caching, you pay full input price for the static part **every single time** — wasteful when it repeats 50,000 times a day!

### How Pricing Works With Caching

| Cache Type | What Happens | Cost Behavior |
|---|---|---|
| **First query (cache write)** | Prompt is processed AND cached | Costs MORE than normal input (e.g., $12.50 instead of $10 per million tokens) — because you're paying for input processing + cache-writing |
| **Subsequent queries (cache hit)** | Cached portion is reused | Costs MUCH LESS (e.g., $1 instead of $10 per million tokens) |

### 5-Minute vs 1-Hour Cache — What's the Difference?

> **Cache Refresh Cycle**: The duration after which cached content is automatically evicted from the server if not reused.

- **5-Minute Cache Write**: If your next query comes within 5 minutes of the last one, you get the cheap cache-hit rate ($1). If it comes after 5 minutes, the cache expires and you pay the expensive cache-write rate again ($12.50).
- **1-Hour Cache Write**: Same logic, but the refresh window is 1 hour instead of 5 minutes.

### Which One Should You Choose?

| Scenario | Recommended Cache | Why |
|---|---|---|
| High-traffic app (e.g., 50,000 queries/day spread across the day) | **5-minute cache** | Queries arrive frequently enough that the cache rarely expires — mostly getting cheap hits |
| Low-traffic app (e.g., ~1,000 queries/day) | **1-hour cache** | Queries are sparse; a longer window increases chance of hitting the cache before it expires |

**Real Example from the lecture:**
- PSP & CricInfo (high traffic, cricket fans query constantly) → 5-minute cache works well since some query always arrives within 5 minutes.
- Exception: At 2 AM, no queries for 3 hours → cache expires → next query at 6 AM pays full cache-write price again, then cheap rate resumes.

### Impact on Cost

> Using prompt caching, a scenario that would cost ₹1 lakh/month **without** caching could potentially be brought down to **₹60–70k/month** — a huge saving!

### When Prompt Caching Does NOT Help

| Application Type | Does Caching Help? | Why |
|---|---|---|
| Text-to-SQL bot (fixed schema + instructions) | ✅ Yes, a lot | Large static portion (schema) repeats every query |
| RAG Chatbot | ❌ Not much | The "context" (retrieved documents) changes with almost every query — nothing stays static long enough to cache |

## ⚙️ KV Caching — The Internal Mechanism {#kv-caching}

> **Definition**: KV (Key-Value) Caching is the underlying technical mechanism that powers prompt caching. It is related to the **Attention Mechanism** inside Transformers, where the **Key (K)** and **Value (V)** vectors computed for a piece of text can be stored and reused instead of recomputing them for every new request.

- This is a deep, advanced topic that will be covered in detail in a future lecture on Transformer internals.
- For now, just understand: **prompt caching is enabled internally by caching K and V vectors from the attention layers**, so the model doesn't need to redo that computation for repeated text.

### 1️⃣ Column Description Problem (Student Question)

**Q asked**: Without column descriptions, how can an LLM understand what data is in the tables?

**Answer**: 
- General/well-known schemas → LLM may infer meaning from column names alone.
- Highly domain-specific/technical column names → You should **explicitly describe each column** in your system prompt (add a paragraph describing the schema).
- **Trade-off**: This makes the system prompt bigger → costs more. But **prompt caching solves this problem** since the schema description becomes part of the static cached portion!

### 2️⃣ Latency Requirements ⏱️

> **Definition**: Latency is the time taken between sending a request and receiving a complete response.

**Key principle**: Latency tolerance depends entirely on the **use case**.

| Use Case | Latency Sensitivity | Why |
|---|---|---|
| Research Assistant (browses internet, compiles report) | Low — latency isn't critical | Users expect some wait for deep research |
| Live Match Q&A App (our case study) | **High** — latency is critical | Users are curious in real-time during a live match; slow answers frustrate them |

**Recommended benchmark**: **2–3 seconds** is a good target.
- Beyond 3 seconds → users start getting anxious ("something's wrong, is my payment stuck?" — an "OCD trigger" as described in the lecture).
- 5 seconds is considered too slow by most users.

**Implication for model choice**: You **cannot** use:
- Models with inherently high latency
- "Reasoning" models that spend a lot of time "thinking" before responding (e.g., extended chain-of-thought models)

### 3️⃣ Context Window Requirements 🪟

> **Definition**: Context window is the maximum number of tokens (input + conversation history) a model can process at once.

**Key Insight from this case study**: For our Text-to-SQL app, **context window does NOT matter much** because:
- Each user query is a **standalone, disjoint question** — no relation to previous questions
- There's **no multi-turn conversation**, no session memory needed
- So even a model with a **small context window** would work fine here

**When context DOES matter**:
| Application | Context Window Importance |
|---|---|
| Text-to-SQL (single-turn) | ❌ Low |
| Chatbot (multi-turn conversation) | ✅ High |
| Coding Assistant (needs to see large codebases) | ✅ High |

### 4️⃣ Deployment Preference — Open Source vs Public API 🌐

**Key Question**: Should you self-host open-source models (for privacy/compliance) or use public APIs (OpenAI, Anthropic, etc.)?

**Decision Rule**:
- If you're handling **sensitive/private data** that legally/ethically must stay on your own servers → self-host open-source models
- If there's **no such data sensitivity** → prefer public APIs

**For our cricket Text-to-SQL app**: No sensitive data involved → **Public APIs are preferred**, and actually recommended because:

> Public API providers (like Anthropic, OpenAI) have superior infrastructure, reliability, and robustness compared to a custom in-house setup, which would require heavy technical teams and still might not match the uptime of a dedicated provider.

### 5️⃣ Correctness / Accuracy Requirements ✅

> **Definition**: Correctness is how accurately/reliably the model produces the right output without hallucinating.

**Why it matters hugely here**: Cricket fans are **extremely finicky about statistics/records**. 

**Real-world risk example**: If asked "Who has scored the most runs in IPL?" and the model hallucinates "Jasprit Bumrah" (a bowler, not known for runs) — a screenshot of this error will instantly go viral on social media, damaging the brand's reputation and market sentiment.

**How to verify correctness**:
1. Check **leaderboards** — since SQL generation is essentially a **coding task**, coding benchmarks are a good proxy
2. Run **custom evals** on your own data/task to measure model accuracy specifically for your use case
