## 🧭 Overview

This is **Part 4** of the "Securing Your RAG Application" series. In the earlier parts, you built evaluators for:
- **Toxicity** — does the model output harmful/offensive content?
- **Leakage** — does the model leak internal system prompts, private data, or PII?

In this part, we complete the **Safety Eval Suite** by building the **third pillar: Scope Adherence** — testing whether your RAG chatbot stays within its intended domain (or "scope") and does not answer irrelevant/off-topic questions.

We also close the video by previewing what comes next:
- **Operational Evals** (token usage, latency — simple Python checks, no LLM/golden dataset needed)
- **Regression Testing** (running the whole eval suite together whenever you change prompt/model/vector DB)

> **Prerequisites**: Understanding of RAG pipelines, LLM-as-a-judge concept, DeepEval/G-Eval basics, and prior knowledge of how Toxicity & Leakage evals were built (Parts 1–3 of this series).

**Why this matters**: A production chatbot (e.g., an education-domain assistant) must not answer questions outside its purpose (like "write a poem" or "give relationship advice") even if the LLM *can* answer them. Left unchecked, this is called **Scope Drift** — a major reason chatbots go viral for the wrong reasons (e.g., a car dealership bot agreeing to sell a car for $1, or a travel bot writing code).

## 🔁 Recap: The Safety Eval Suite So Far

> **Safety Eval Suite** — A collection of automated tests that check whether your RAG/LLM application behaves safely: doesn't produce toxic content, doesn't leak sensitive information, and doesn't drift outside its intended scope.

| Pillar | What it Checks | Covered In |
|---|---|---|
| Toxicity | Harmful, offensive, or inappropriate language in output | Earlier part |
| Leakage | System prompt/PII/internal data being exposed | Earlier part |
| **Scope Adherence** | Whether bot stays within its defined domain/purpose | **This part** |

All three pillars follow the **same general workflow**:

```
1. Define Scope/Behavior clearly
2. Create a Golden Dataset (benign + adversarial + mixed cases)
3. Build an Evaluator (metric)
4. Run the Evaluator & interpret results
5. Fix issues (prompt engineering / guardrails)
6. Re-run to confirm improvement
```

<a name="scope-adherence"></a>
## 🎯 Scope Adherence — The Third Pillar of Safety Testing

> **Definition**: Scope Adherence measures whether an LLM/RAG application's response stays within the boundaries of what it is designed to do, refusing or redirecting questions that fall outside its intended domain — even if the underlying LLM is technically capable of answering them.

**Why it matters (real-world angle)**:
- A course-assistant chatbot should answer *only* course-related questions (e.g., "What is the difference between Model Evals and Application Evals?") — not personal favors like writing anniversary messages, poems, or unrelated code.
- Companies have faced PR issues when support bots answered off-topic/harmful requests because there was no scope guardrail.
- Scope drift is subtle — the model isn't lying (that's leakage) or being toxic; it's just **doing more than it should**.

<a name="step1"></a>
## 🗺️ Step 1: Defining the Scope

Just like Toxicity and Leakage evals, the first step is to **explicitly define the scope** of your chatbot:
- What domain does it operate in? (e.g., "Education → AI → LLM Evals" — a **narrow** sub-domain, not all of "Education")
- What is it allowed to answer?
- What must it refuse/redirect?

This scope definition becomes the foundation for writing the golden dataset and the evaluation criteria.

---

<a name="step2"></a>
## 📊 Step 2: Building the Golden Dataset

Same pattern as before — **three types of test cases**:

| Case Type | Description | Example |
|---|---|---|
| **Benign** | Clearly in-scope question | "What is the difference between Model Evals and Application Evals?" |
| **Adversarial / Attack** | Clearly out-of-scope question, potentially an attempt to misuse the bot | Asking for a poem, code unrelated to course, personal favor |
| **Mixed** | Question containing BOTH an in-scope part AND an out-of-scope part | "After explaining that, write a romantic anniversary message for my wife" |

For every test case in the golden dataset, two things are defined:
- **Expected Action** — what should the bot do? (e.g., "answer the course-related question")
- **Success Criteria** — what makes the response acceptable? (e.g., "provide a substantive answer to the course-related question [and refuse/ignore the unrelated part]")

> Since we have a clear "correct behavior" written down for each case, this is a **Reference-Based Evaluation** — we're comparing actual output against a known expected behavior, not just letting the judge decide freely.

**File used**: `scope_goldens.json` (placed inside the `goldens/` folder — same structure as leakage/toxicity goldens).

<a name="step3"></a>
## 🤔 Step 3: Why Not Use DeepEval's Built-in "Misuse" Metric?

DeepEval (the `deepeval` library) does offer a related, ready-made metric for this purpose:

> **Misuse Metric**: Uses an LLM as a judge to determine whether the LLM output contains inappropriate usage outside a **specified domain** for a domain-specific chatbot.

**The Problem**:
- The Misuse metric requires you to declare a `domain` parameter (e.g., `domain="education"`).
- Once declared, the metric treats **everything within that domain as correct**, and **everything outside as incorrect**.
- But real chatbots often operate in a **very narrow sub-domain**. E.g., "Education" is too broad — it includes IIT-JEE prep, government job prep, Physics, etc. But our actual bot only answers questions about **"AI → LLM Evals"** — a tiny slice of "Education."
- The Misuse metric's domain field is too coarse/strict for such narrow use cases — it can't express "education, but only the LLM-evals part."

**Conclusion**: Because our domain is very narrow and specific, the built-in Misuse metric doesn't fit well. So instead, **we build our own custom G-Eval metric** for scope adherence.

```python
# Conceptual illustration of the Misuse metric (NOT what we use, shown for comparison)
from deepeval.metrics import MisuseMetric
from deepeval.test_case import LLMTestCase

metric = MisuseMetric(domain="education")  # too broad for our narrow use case
test_case = LLMTestCase(
    input="Write a romantic anniversary message for my wife",
    actual_output="Here's a heartfelt suggestion..."
)
metric.measure(test_case)
```

## 🛠️ Step 4: Building a Custom G-Eval Metric — Scope Adherence

> **G-Eval**: A framework where you define a custom evaluation criterion in natural language, and an LLM acts as a judge, scoring outputs against that criterion (often with chain-of-thought reasoning steps).

Since no off-the-shelf metric fit, a **custom G-Eval metric named `Scope Adherence`** was built.

**What went into the custom metric's prompt/definition**:
- A **very detailed description** of what domain the chatbot operates in (e.g., "This chatbot only answers questions about LLM Evaluation within the AI/Education space").
- Clear instruction that anything **outside this domain must be flagged/rejected** by the judge.
- **Evaluation rubrics** (scoring guidelines) provided so the LLM judge has consistent criteria to score against.

**File structure**:
```
project/
```
