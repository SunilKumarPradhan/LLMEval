## 🧪 Regression Testing — Deep Dive {#regression-testing}

> **Definition:** **Regression testing** means re-running your evaluation suite every time you make a change to your RAG software, and comparing the new results against a **baseline** to check whether the change improved or degraded the system.

The core idea: *Software changes constantly (new prompt, new chunking strategy, new model, new retriever config). Every change is a gamble — did it help or hurt?* Regression testing removes the guesswork by making comparison systematic.

There are **three levels of maturity** for doing regression testing — you evolve through them as your engineering practice matures.

### 🥉 Level 1: Simple/Manual Regression Testing

**How it works:**
1. Run your evaluation suite **once** → this becomes your **baseline** (a set of metric numbers).
2. Every time you make a change to the software, run the eval suite again → get a **new set of readings**.
3. **Manually compare** new readings vs baseline to judge if performance improved or dropped.

**Limitation:** Manual comparison doesn't scale. No visual tracking, no history, easy to forget past baselines, error-prone at scale.

**When to use:** Small teams, early-stage projects, solo developers, quick prototyping.

### 🥈 Level 2: Automated with Experiment Tracking (e.g., MLflow)

**How it works:**
- Instead of manually noting numbers, you use an **experiment tracking tool** (like MLflow).
- Every time the eval pipeline runs, metric values are **automatically logged** according to your configuration.
- You can view all historical runs on a **visual dashboard** — compare runs, track trends over time.

**Why it's better:** No manual number-crunching; you get a persistent, queryable, visual history of every experiment/version.

**When to use:** Growing teams, multiple team members iterating on the RAG app, need for historical comparison and accountability.

### 🥇 Level 3: CI/CD-based Gating Mechanism (Full Automation)

**How it works:**
- Bring in a **CI (Continuous Integration) tool** into the picture.
- Every time the eval pipeline runs (e.g., triggered by a code push), the CI tool **automatically**:
  1. Runs the new evaluation suite → gets new metric readings.
  2. Compares new readings against the current baseline.
  3. Applies a **threshold rule** (e.g., "new score should not be more than 3 points lower than baseline").
  4. **Decision:**
     - ✅ If new metrics are **better or within threshold** → **allow deployment** and **update baseline** to new metrics.
     - ❌ If new metrics are **worse than threshold** → **block/pause deployment** (regression detected — software has deteriorated).

> **Definition (Gating Mechanism):** A gating mechanism is an automated checkpoint that only allows a deployment to proceed if it passes certain quality criteria — here, it means your RAG app only gets deployed if it doesn't score worse than the current baseline.

**Why it's powerful:** This lets engineering teams **ship changes fearlessly and continuously**. You can keep experimenting and pushing changes; the system automatically filters out anything that harms quality. No manual gatekeeping needed.

```
   New Code/Change Pushed
            |
            v
   CI Triggers Eval Pipeline
            |
            v
   New Metrics Generated
            |
            v
   Compare vs Baseline (with threshold)
      /                  \
  Better/OK           Worse (regression)
     |                      |
     v                      v
 Deploy & Update       Block Deployment
   Baseline             (reject change)
```

**When to use:** Mature engineering teams, production-grade LLM/RAG apps, teams practicing MLOps/LLMOps, when you need to move fast without breaking quality.

## 🚀 Deployment & Beyond {#deployment}

Once regression testing confirms the new version is better than the baseline:
- **Deploy the software.**
- The **baseline updates** to reflect the new (deployed) version's metrics.

> ⚠️ **Critical Concept:** Evaluation does **NOT stop** after deployment. This is a common misconception — many think "we tested it, it works, we're done." In reality, **production behavior can differ from test-time behavior**, so continuous evaluation is essential. This post-deployment evaluation is called **Online Evaluation**.

## 🌐 Online Evaluation — Deep Dive {#online-evaluation}

> **Definition:** **Online evaluation** is the continuous monitoring and evaluation of a RAG application **after it has been deployed and is live**, using real user interactions rather than a fixed offline dataset.

Once live, you do **four main things**:

### 1️⃣ Captured Signals (Tracing / Observability)

These are raw signals captured **as they happen**, in real time, from actual user interactions:

| Signal | What it Means |
|---|---|
| **Latency** | How long it takes to answer a user's question |
| **Cost** | Token/API cost per interaction |
| **Tokens** | Number of tokens consumed |
| **User Feedback** | Thumbs up / thumbs down from real users |

> **Definition (Tracing/Observability):** In the LLM world, adding "tracing code" to your application to capture every interaction's metadata (latency, cost, tokens, feedback) and viewing it all in a unified dashboard is called **tracing** or **observability**.

**Tools mentioned for this:** LangSmith, Langfuse, Confident AI.

**How it works technically:**
- You add tracing code inside your RAG application.
- Every live interaction gets logged with its metadata.
- All of this appears on a dashboard (e.g., LangSmith dashboard) for easy visualization.

### 2️⃣ Computed Metrics (Online)

Beyond just capturing raw signals, you also **compute quality metrics live** — essentially re-running some of your **offline metrics on live/online data**:
- Online **Faithfulness**
- Online **Answer Relevance**
- Online **Correctness**

> This means: the same rigor you applied offline (during evaluation suite testing) is now applied continuously to real production traffic.
