## Overview

## Recap: Why We Need Golden Datasets

> **Golden Dataset**: A manually curated, trusted dataset that tells us "for this input query, this is the correct/expected output." It acts as ground truth against which we measure our system.

To answer the question **"Is my retriever's recall high or low?"**, we first need to know **what the "correct context" looks like for every query**. Since a human must define what "correct" means, this automatically makes the evaluation **reference-based**.

---

## Reference-Based vs Reference-Free Evaluation

> **Reference-based evaluation**: Requires a "gold standard" (golden dataset / golden context) to compare against. You need someone to tell you what the *correct* answer/context is.

> **Reference-free evaluation**: Does NOT require a pre-defined correct answer; the metric can be computed purely from the query, retrieved context, and/or generated answer.

Both **Recall** and **Precision** (as discussed here) are **reference-based metrics** — they cannot be computed without a golden dataset and golden context.

📌 **Why this distinction matters:** Over the next few classes, many different RAG evaluation metrics will be introduced. Some will need a golden dataset (reference-based), others won't (reference-free). Keeping this mental model clear helps you understand *why* a metric needs certain inputs and *when* it's practical to use.

## Method 1: The "Naive" Golden Dataset (Question + Chunk IDs)

This is the first (intuitive) approach to building a golden dataset for retriever evaluation.

**Structure:**

| Question | Correct Chunk IDs |
|---|---|
| What is Regression Testing? | 72, 89, 100 |
| What is RAG Triad? | 120, 111 |
| What are Online Evals? | 151, 121, 130 |

- Someone (a domain expert) manually studies **all chunks** in the vector database and notes down which chunk IDs are relevant to each question.
- This is repeated for ~50 (or more) questions to build the full golden dataset.

## Calculating Recall — Method 1

**Step-by-step process:**

1. Take a query from the golden dataset → e.g., *"What is Regression Testing?"*
2. Send it to the retriever (with `k = 5`, i.e., top 5 chunks are fetched).
3. Retriever returns: `72, 81, 89, 99, 100`
4. Compare against golden chunk IDs: `72, 89, 100`
5. Count how many golden chunks were actually retrieved.

$$
\text{Recall (per query)} = \frac{\text{Number of relevant chunks retrieved}}{\text{Total relevant chunks that exist}}
$$

**Example 1:** Golden = {72, 89, 100}, Retrieved = {72, 81, 89, 99, 100}
→ All 3 relevant chunks found → Recall = 3/3 = **1.0**

**Example 2:** Golden = {120, 111}, Retrieved = {1, 2, 3, 120, 5}
→ Only 120 found → Recall = 1/2 = **0.5**

Repeat for all 50 queries → take the **average** → this gives the **overall/average Recall** of the retriever.

```python
# Conceptual illustration (not from transcript code, just explanatory)
def recall_at_k(retrieved_ids: list, golden_ids: list) -> float:
    """
    retrieved_ids: chunk IDs returned by the retriever (top-k)
    golden_ids: chunk IDs marked correct in the golden dataset
    """
    relevant_found = len(set(retrieved_ids) & set(golden_ids))
    return relevant_found / len(golden_ids)

# Example
golden = [72, 89, 100]
retrieved = [72, 81, 89, 99, 100]
print(recall_at_k(retrieved, golden))  # 1.0

# Average recall over all queries
recalls = [recall_at_k(r, g) for r, g in zip(all_retrieved_lists, all_golden_lists)]
average_recall = sum(recalls) / len(recalls)
```

## Calculating Precision — Method 1

Precision asks: **"Of all the chunks retrieved, how many were actually useful (not noise)?"**

$$
\text{Precision (per query)} = \frac{\text{Number of relevant chunks retrieved}}{\text{Total chunks retrieved}}
$$

**Example 1:** Retrieved = `{72, 81, 89, 99, 100}`, Golden = `{72, 89, 100}`
→ 3 correct out of 5 retrieved → Precision = 3/5 = **0.6**

**Example 2:** Retrieved = `{1, 2, 3, 120, 5}`, Golden = `{120, 111}`
→ 1 correct out of 5 → Precision = 1/5 = **0.2**

Again, repeat for all queries → **average precision**.

```python
def precision_at_k(retrieved_ids: list, golden_ids: list) -> float:
    relevant_found = len(set(retrieved_ids) & set(golden_ids))
    return relevant_found / len(retrieved_ids)
```

Together, **average Recall** + **average Precision** tell you how well your retriever is performing.

## Why Method 1 Fails in Practice

This is the **core insight** of this section — a very important "why" discussion.

> ⚠️ The chunk-ID-based golden dataset approach is logically correct but **practically broken** for most real-world RAG applications (especially where content is interrelated across documents).

### Problem 1: Insane manual effort

- Someone has to **manually read every single chunk** (in this example, **800+ chunks**) for **every single question** (e.g., 50 questions) to figure out which chunks are relevant.
- That's up to 800 × 50 = 40,000 comparisons done manually. Nobody wants this job — it's extremely tedious and error-prone.

### Problem 2: Chunking parameters change → chunk IDs become invalid

- Suppose recall comes out to be **65%** (not good). A natural fix: increase `k` (e.g., 5 → 8), OR tweak **chunking parameters** (e.g., chunk_size 750 → 1000, overlap 100 → 150).
- The moment you change chunking parameters:
  - The **chunks themselves change** (different boundaries, different content per chunk).
  - The **vector database must be rebuilt** from scratch.
  - Chunk **IDs shift** — what was chunk 72 before may no longer correspond to the same content, or may not even exist (e.g., 800 chunks might become 700).
  - This makes your **entire golden dataset invalid (void)**.
- Result: **Every time** you tune chunking parameters, you must **rebuild the golden dataset** — repeating the painful manual process.

> ❌ This is called *"a very bad example of engineering"* — it doesn't scale, and it discourages iteration/experimentation, which is essential in ML/RAG system tuning.

### When Method 1 *can* actually work

There ARE valid use cases:

- When documents are **cleanly separated and independent** (Document 1 is very different from Document 2, no overlapping information).
- When you **don't plan to tweak chunking parameters** frequently (chunk size is fixed once and stays fixed).

In such cases, chunk IDs remain stable, and this approach is acceptable.

But in typical RAG apps (like lecture transcripts where the same concept — e.g., "Regression Testing" — might be discussed in **Session 1 and Session 5**, i.e., info spread across documents), this method breaks down because chunking parameters *will* need tuning.
