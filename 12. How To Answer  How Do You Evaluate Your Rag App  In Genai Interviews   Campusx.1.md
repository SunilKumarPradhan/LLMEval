## <a name="overview"></a>🎯 Overview

This lecture is the **starting point of Application Evals** in the LLM Evaluation playlist — arguably the most important and most frequently tested topic in GenAI interviews. The famous interview question this section prepares you for is:

> **"How do you evaluate your RAG application?"**

This question is asked in **8 out of 10 GenAI interviews**, and most candidates fail to answer it in a structured way — either because they never studied evals, or because they only know isolated metrics without a coherent framework.

**Prerequisites:** You should already know:
- Basic RAG architecture (retriever, generator, vector database, embeddings)
- The difference between model evals and application evals (from earlier lectures)
- Reference-based vs reference-free evals, online vs offline evals

**Why this matters:** Real-world GenAI products (chatbots with RAG, agentic systems) require rigorous, multi-layered testing — just like traditional software needs unit tests, integration tests, and system tests. This lecture builds that exact mental model for RAG applications.

## <a name="app-types"></a>🧩 Types of LLM-Based Applications

Before evaluating any application, you must recognize that "LLM-based application" is a broad umbrella term. Different types include:

| Type | Description | Example |
|---|---|---|
| **Simple Chatbot** | No retrieval, no tools — just LLM + prompt | Basic Q&A bot |
| **RAG-based Chatbot** | Retrieves external context before generating answer | Customer support bot with knowledge base |
| **Agents** | LLM that can use tools, take actions, make decisions | Autonomous task-solving agent |
| **Multimodal Apps** | Interaction happens in modalities other than text | Image generator |
| **Fixed Schema Output Apps** | LLM outputs must follow a strict structured format | Zomato email classifier (support/refund/technical) |

> 💡 **Definition:** A **fixed schema output application** is one where the LLM's job is to produce output conforming to a predefined structure — e.g., classifying an email into a fixed set of categories.

## <a name="why-rag-agents"></a>🎯 Why RAG & Agents Are Chosen for Deep Study

The instructor explicitly chose to teach **only two** types of application evals in depth:

1. **RAG** — because most professional chatbots you'll build will have RAG functionality baked in.
2. **Agents** — because agentic systems are becoming increasingly important in production.

**Why not the others?**
- Simple chatbots (no RAG, no agent) → considered "easy" once you know RAG/agent evals; skills transfer down.
- Multimodal apps → different, but less common in production (few companies/projects are truly multimodal).

> 💡 **Rule of thumb:** If you master evaluating the *hard* things (RAG, Agents), you can automatically handle the *easier* things.

## <a name="case-study"></a>📘 Case Study: CampusX Doubt Solver

To keep the focus on **evaluation** (not on building something fancy), a deliberately **simple** RAG problem statement was chosen.

**Problem Statement:**
- CampusX runs an LLM course with ~2 lectures/week.
- Each lecture comes with a **recording + transcript**.
- All these transcripts become the **knowledge base documents**.
- Build a **RAG chatbot** ("Doubt Solver") that lets students ask any doubt from the course, and the bot retrieves relevant transcript chunks to answer.

> 💡 **Note:** The instructor does not re-explain how RAG works internally (retriever + generator + vector DB + embedding model) — that's assumed prior knowledge.

**Why this problem statement?**
- Simple enough that building isn't the focus.
- Rich enough (real documents, real doubts) that evaluation becomes meaningful and fun to explore in depth.

## <a name="rag-architecture"></a>🏗️ RAG Architecture Refresher

```
                 ┌─────────────────┐
   Query ───────▶│  Vector Database │
                 └────────┬─────────┘
                          │ (top-k relevant docs)
                          ▼
                 ┌─────────────────┐
                 │    RETRIEVER     │──▶ Question + Relevant Context
                 └────────┬─────────┘
                          │
                          ▼
                 ┌─────────────────┐
                 │    GENERATOR     │──▶ Final Answer
                 │      (LLM)       │
                 └─────────────────┘
```

- **Vector Database:** Stores all documents as embeddings (vectors).
- **Retriever:** Takes the incoming query, searches the vector DB, and returns the top-k most relevant documents (context) along with the original question.
- **Generator (LLM):** Takes the question + retrieved context and produces the final answer.

This is the standard **Retriever → Generator** pipeline that forms the backbone of any RAG system.
