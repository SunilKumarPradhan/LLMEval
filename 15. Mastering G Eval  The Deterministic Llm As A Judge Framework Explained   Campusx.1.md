## <a name="five-metrics"></a>📏 The Five Count-Based Metrics (Recap)

So far, five metrics have been covered to evaluate a RAG pipeline:

1. **Recall**
2. **Precision**
3. **Faithfulness**
4. **Answer Relevance**
5. **Context Relevance**

### Example Walkthrough: Faithfulness

> **Faithfulness** checks whether the generator's answer is completely derived from the retrieved context, or whether the generator "invented" some information on its own (hallucination).

**How it was calculated (old method):**

```
Step 1: Take the generated answer
Step 2: Use an LLM to break it into individual "claims" (Claim 1, Claim 2, Claim 3, Claim 4...)
Step 3: For each claim, ask: "Does this claim exist in the context?"
Step 4: Count how many claims are supported by context
Step 5: Faithfulness Score = (Supported Claims) / (Total Claims)
```

**Example:** If 3 out of 4 claims are found in the context → Faithfulness Score = 3/4 = 0.75

---

## <a name="pattern"></a>🔍 The Pattern Behind Count-Based Metrics

> **Definition:** All five metrics above are **"Count-Based Metrics"** — they work by breaking an answer into discrete units (claims), checking each unit against a reference (context/expected answer), and computing a **ratio** (count of favorable / total count).

**Common workflow across Recall, Precision, Faithfulness, Answer Relevance, Context Relevance:**

```
1. Use an LLM to break down text into claims/statements
2. Check each claim against a reference (context, question, etc.)
3. Count favorable vs unfavorable claims
4. Compute a ratio-based score using a formula
```

This works great **when the concept of "counting" makes sense** — i.e., when a text can be meaningfully broken into independent, checkable units.

## <a name="breakdown"></a>⚠️ When Count-Based Methods Break Down

Not all metrics fit this counting pattern. Two examples illustrate this:

### Example 1: Style Evaluation

**Problem:** We want to check if an answer follows "CampusX's teaching style" (say, a "Why-What-How" structure).

- If you break the answer into individual sentences/statements and check each one for "Why-What-How" — **it won't work**, because the Why-What-How pattern exists at the **whole-answer level**, not at the sentence level.
- **Conclusion:** Style cannot be measured by counting; it needs **holistic judgment** of the entire answer.

### Example 2: Correctness Evaluation

**Problem:** We want to check if a generated answer is factually correct by comparing it against a golden (correct) answer.

- Naive approach: Break the answer into claims, check each claim against the golden answer, count matches.
- **Flaw:** Not every claim is *directly* comparable to the golden answer in isolation.
  - **Example:** If the chatbot uses an **analogy** to explain a concept, and you evaluate that analogy claim in isolation against the golden answer, it will appear "unrelated" and get falsely penalized — even though the analogy makes perfect sense **within the context of the full answer**.
- **Conclusion:** Correctness also often needs **whole-answer level judgment**, not claim-level counting.

> **Key Insight:** Metrics like Style, Correctness (in certain cases), Completeness, Helpfulness, and most Safety-related metrics fall into a category where **counting doesn't work** — you need **judgment** instead (either human judgment or LLM judgment).

## <a name="judgment-based"></a>⚖️ Introducing Judgment-Based Metrics

> **Definition:** Judgment-based metrics require someone (human or LLM) to **read the entire answer holistically** and assign a score (e.g., 1–5 or 0–10) based on a qualitative criterion — no ratio or counting involved.

Today's three metrics — **Correctness, Completeness, Style** — are all **judgment-based metrics**. This requires using an **LLM as a Judge** to directly generate a score.

---

## <a name="naive-approach"></a>🧪 Naive LLM-as-a-Judge Approach (Step-by-Step)

Let's walk through how a naive/straightforward LLM-as-a-judge approach works for measuring **Correctness**.

### Step 1: Prepare a Golden Dataset

> **Golden Dataset**: A set of Question–Correct Answer pairs where the "correct answer" is the universally accepted answer (e.g., matches what you'd find on Google), not necessarily what was taught in class.

Example structure (assume 15 rows):

| Question | Expected (Golden) Answer |
|---|---|
| Q1 | A1 |
| Q2 | A2 |
| ... | ... |
| Q15 | A15 |

### Step 2: Generate Actual Answers

Feed each question from the golden dataset into your RAG chatbot → get the **Actual (Generated) Answer**.

### Step 3: Build a Simple Judge Prompt

```
You are evaluating whether an AI answer is correct.
You will be given a Question, an Expected Answer, and the Actual Answer.

Compare the actual answer against the expected answer and decide 
how factually correct it is. Give a score from 0 to 10 where 
10 = fully correct and 0 = completely wrong.

Question: {question}
Expected Answer: {expected_answer}
Actual Answer: {actual_answer}
```

### Step 4: Get a Score, Repeat, and Average

- Feed this prompt to an LLM judge → get a score (0–10) for each of the 15 questions.
- Average all 15 scores → final **Correctness Score** for the RAG application.

### Key Difference vs Count-Based Metrics

| Aspect | Count-Based (old) | Judgment-Based (new) |
|---|---|---|
| LLM's role | Small task: break into claims + check membership | Big task: full holistic judgment |
| Scoring | Ratio (favorable/total) | Direct number given by LLM (0-10) |
| Complexity | More steps, but more structured | Fewer steps, seems "easier" |

> This naive approach is *simpler* to implement than the count-based methods — but simplicity comes at a cost, discussed next.

## <a name="variance-problem"></a>🚨 The Big Problem: High Variance

**Question posed:** Does this naive approach work well in practice?

**Answer: No** — while it works *theoretically*, it's **not a reliable evaluation method** in practice.

> **The Core Issue:** If you run the *exact same evaluation* (same question, same expected answer, same generated answer) multiple times, the score should stay roughly the same. But with the naive LLM-as-judge approach, **the score fluctuates significantly** across runs — e.g., one run gives 6, another gives 7, another gives 8 — even though nothing changed.

This is called **high variance** — and it makes the evaluation **unreliable**.

**Compare with prior (count-based) metrics:** Re-running those evaluations typically produced small fluctuations (e.g., 85 → 86 or 84), NOT big jumps (e.g., 75 → 85). That's the standard of reliability we expect.
