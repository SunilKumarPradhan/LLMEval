## Overview

This lecture is part of a CampusX series on **LLM Evaluations (LLM Evals)**. Having already covered *why* LLM evaluations are needed and how they differ from traditional software testing, this lecture dives into the **core concept**: what exactly are LLM Evals, and how are they categorized.

**Prerequisites:** Basic understanding of what an LLM is, and some familiarity with how LLM-powered applications (like RAG chatbots) are built.

**Why this matters:** Without a clear mental model of what "evaluation" means in the LLM world, engineers tend to do random, unstructured ("vibe") testing. This lecture builds the foundation for a career in AI Engineering — understanding evals correctly helps you decide which LLM to use in a project, and how to systematically judge whether your application is production-ready.

## What are LLM Evaluations?

> **Definition:** LLM Evals are **systematic, repeatable tests** used to judge an LLM or an LLM-powered system against **clear criteria**.

Breaking this definition down, LLM Evals are essentially **tests** applied to:
- LLMs themselves, OR
- LLM-based applications (like chatbots, RAG systems, agents)

This definition has **three critical characteristics** that must always hold true.

---

## The Three Pillars of LLM Evals

### 🧩 1. Systematic
Evals should **not** be "vibe testing" — i.e., you can't just throw 5 random questions at your chatbot, feel satisfied with the answers, and call it "tested."

Instead, systematic testing means:
- You **create proper datasets**
- These datasets attempt to cover **every edge case**
- Real-world example: For a CampusX chatbot, you'd randomly sample **100 real user conversations**, build a dataset from them, and test your system against that dataset — this way you get real-world behavior insights, not guesses.

### 🔁 2. Repeatable
This means if you change:
- The prompt
- The model
- The retriever
- The chunking strategy

...you should still be able to evaluate your system **in exactly the same way** as before.

**Why it matters:** Repeatability lets you fairly **compare Version 1 vs Version 2** of your system using the *same* test dataset. This is how you objectively measure whether your system is *actually improving* over time — not just guessing.

### 🎯 3. Clear Criteria
Evaluations depend heavily on **what criteria** you're judging against. For example, for a CampusX chatbot, criteria might include:
- ✅ Is the answer **correct**?
- ✅ Is the explanation **simple**?
- ✅ Does the explanation come strictly from **course content**?
- ✅ Is the response **safe** (no abusive language, no threatening tone)?

> Without criteria → Vibe testing.
> With criteria → Proper Evaluation.

## Common Misconception: Evals ≠ Just Metrics

Many people (especially those coming from classical ML/DL backgrounds) assume "evaluation" simply means **metrics** — like Accuracy, Precision, Recall in traditional ML.

**This is WRONG for LLM Evals.**

> **Important Clarification:** LLM Eval is NOT just a metric. It is the **ENTIRE testing setup**.

The "entire setup" includes:

| Component | Example |
|-----------|---------|
| What are we testing? | e.g., the Retriever inside a RAG chatbot |
| What criteria are we using? | e.g., Retriever accuracy |
| What dataset are we using? | The curated eval dataset |
| When are we running the test? | Offline, or post-production deployment |
| What tools are we using? | e.g., RAGAS (for RAG applications) |

**Mnemonic:** *What* to test + *On what basis* to test + *When* to test + *Which tool* to use = **LLM Eval**

## Questions LLM Evals Answer

The goal of an LLM Eval is **not** to hand you a single score — it's to answer **practical, actionable questions**, such as:

- 🤔 Can the model be used for a particular task/application?
- 🚀 Is this system good enough to ship (production-ready)?
- 📈 Did Prompt v2 improve over Prompt v1?
- 🔗 Is the RAG answer grounded in retrieved context?
- ✅ Is the agent completing the task correctly?
- 🛡️ Is the chatbot safe for real users?
- ⏱️ Is the latency under control?

## Two Types of LLM Evals

This is the **most important distinction** of the lecture. LLM Evals split into two broad categories:

```
                LLM Evals
                    │
        ┌───────────┴───────────┐
        │                       │
   Model Evals           Application Evals
   (Evaluate the         (Evaluate the entire
    LLM itself)           LLM-powered system)
```

> ⚠️ **Disclaimer (from instructor):** The terms **"Model Evals"** and **"Application Evals"** are **NOT official industry terminology** — they're simplified terms coined by the instructor for teaching purposes. In the industry, both are just called "LLM Evals," and people infer from context which type is being discussed.

This dual categorization comes directly from the original definition: *"...used to judge an LLM **and/or** LLM-powered systems..."* — hence two types.

## Deep Dive: Model Evals

> **Definition:** Model Evals evaluate **the model itself**. The main idea is to test and evaluate the **capabilities** of a model.

**Purpose:** When a new LLM is released, companies test its capabilities and **benchmark** them, then **document and publish** results (e.g., "our model topped X leaderboard with Y% accuracy").

### 🧠 The 8 Core Capabilities Tested in Model Evals

| # | Capability | What it Checks |
|---|-------------|-----------------|
| 1 | **Reasoning** | Can the model solve problems step-by-step? |
| 2 | **Knowledge** | Does it have general/world knowledge (up to its training cut-off date)? |
| 3 | **Basic Maths** | Can it solve mathematical problems? |
| 4 | **Coding** | Can it write/understand code? |
| 5 | **Instruction Following** | Can it follow multiple (e.g., 10) instructions sequentially and correctly? |
| 6 | **Long Context Handling** | Can it extract correct answers from very large context windows? |
| 7 | **Multimodal Understanding** | Can it understand/generate images, text, audio together? |
| 8 | **Tool Use** | Can it correctly utilize external tools/APIs? |

### 📊 Popular Benchmarks per Capability

| Capability | Benchmark |
|------------|-----------|
| General Knowledge & Reasoning | **MMLU** (Massive Multitask Language Understanding) — tests across Science, History, Law, Medicine, etc. |
| Maths | **GSM8K** — grade-school math problems |
| Coding | **SWE-bench**, **HumanEval** |
| Instruction Following | **IFEval** |
| Long Context | **Needle in a Haystack** |
| Multimodal | **MMMU** |

> 💡 These benchmarks will be covered in detail in the **next lecture**, including how they're applied to LLMs and how results are extracted.

### 👨‍💻 Should You (as an AI Engineer) Do Model Evals?

**Short answer: Mostly NO — but you should be LITERATE in them.**

- Benchmarking new LLMs is the job of **Frontier AI Labs** (OpenAI, Anthropic, Google, etc.) — not typical AI application engineers.
- However, you **must** know:
  - What model evaluation means
  - What benchmarks exist and what they measure
  - **How to read** benchmark results
- **Why this matters practically:** When starting a new project, you need to decide *which LLM to use* (OpenAI vs Anthropic vs open-source). This decision-making is powered by knowledge of Model Evals/benchmarks — even though you won't be running these evals yourself.

## Deep Dive: Application Evals

> **Definition:** Application Evals assess the **behavior and performance of an LLM-powered application** — either at the level of the **entire system** or a **specific component** within it.

This is the **MAIN topic of this entire course/playlist**. As an AI Engineer, your job is to **build** LLM-based applications — so evaluating them is also **your responsibility**.
