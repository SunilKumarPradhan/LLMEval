## 🔁 Quick Recap: Why & What of LLM Evals {#recap}

> **LLM Evals** — Evaluations are systematic processes to measure how well an LLM or an LLM-based application performs on a given task.

Two types were discussed earlier:

| Type | Focus |
|------|-------|
| **Model Evals** | Evaluating the raw foundation model itself (e.g., benchmarks like MMLU, HellaSwag) |
| **Application Evals** | Evaluating a real-world product/system built using an LLM (e.g., a chatbot, a routing system, a RAG pipeline) |

This lecture focuses entirely on **Application Evals**, since that's what most engineers work on daily.

## 🏢 Case Study: Zomato Email Classifier {#case-study}

### The Business Problem

You are engineers working at a company (let's imagine it's **Zomato**). The company receives a **huge volume of customer emails daily**. Manually reading and replying to each one is inefficient and expensive.

### The Goal
Automate the process of:
1. Reading the email content
2. Classifying it into one of three categories:
   - **Billing** issue
   - **Technical** issue
   - **General** query
3. Routing it automatically to the correct team:

```
Email → LLM Classifier → Routing Decision
                          ├── Billing Query   → Billing Team
                          ├── Technical Query → Technical Team
                          └── General Query   → Customer Support Team
```

### The Solution (Naive Version)
A single LLM is given a system prompt like:

```
You are a customer support agent. Read the email content 
and classify it as one of: Billing, Technical, or General.
```

This is an extremely simple LLM application — buildable in "5-10 minutes."

### 🚨 The Real Question
**Can we deploy this directly?**

**NO.** Before deployment, we must **evaluate** the system to ensure it actually works reliably. This is where the full workflow comes in.

### 🔹 Step 1: Define Task & Target

> **Definition:** Before evaluating anything, you must clearly state *what* you're evaluating (the target/system) and *what task* it performs.

- **Target:** The Zomato email routing system (the whole workflow)
- **Task:** This is a **classification task** — check if the system correctly classifies emails into Billing / Technical / General.

**Why this matters:** Without a clearly defined task and target, you cannot design meaningful metrics or datasets later.

---

### 🔹 Step 2: Define Success Criteria

> **Definition:** Success criteria answers: *"How would we know the system is working correctly?"* It defines the metric used to judge performance.

For this classification task:
- **Success Criteria:** Classification correctness
- **Metric:** **Accuracy**

**Example:**
- 100 queries sent → 90 correctly routed → System is **90% accurate**

**Why Accuracy here?** Because the output is a discrete category (Billing/Technical/General), making it trivially comparable to the ground truth label — perfect for a simple metric like accuracy.

---

### 🔹 Step 3: Build a Dataset (Golden Dataset)

> **Definition:** A **Golden Dataset** is a labeled dataset where each input (email) has a manually verified correct output (label), used as ground truth for evaluation.

**Structure:**

| Email Content | Correct Label |
|----------------|----------------|
| "My card was charged twice" | Billing |
| "The app crashes on login" | Technical |
| "What are your hours?" | General |

**Real-world practice:**
- Typically **50–500 rows** of data (sometimes much more)
- Best source: **actual historical data** (e.g., Zomato's past customer chat logs)
- Labeling is usually done **manually** by a human (or team) to ensure accuracy

**Why it's called "Golden":** It represents the trusted, verified truth against which all model outputs are measured — like a gold standard.

---

### 🔹 Step 4: Define Evaluation Method

> **Definition:** This step decides **WHO/WHAT will judge** whether the system's output matches the expected output.

Three options:

| Method | When to Use | Example |
|--------|-------------|---------|
| **Automated (Code-based)** | Output is structured/discrete (e.g., a single label) | Python script comparing `predicted_label == actual_label` |
| **Human Evaluation** | Output is unstructured/long text needing subjective judgment | Reading long chatbot responses |
| **LLM-as-a-Judge** | Middle ground — output is complex text, but you can't afford full human review at scale | Using another LLM to score answer quality |

**Why the choice matters:**
- For our simple classifier (Billing/Technical/General), comparing 2 labels is trivial → **use Automated (Python code)**. No need to spend money on humans or LLMs.
- If instead this was a **chatbot** producing long paragraph answers, comparing two paragraphs semantically is NOT something plain code can do reliably (a code-based string match can't judge if two answers "mean the same thing"). Options then narrow to:
  - **Human** → accurate but **costly** and slow
  - **LLM-as-a-Judge** → a good middle-ground: faster and cheaper than humans, more nuanced than code

> **Key takeaway:** Choice of evaluation method depends on the **nature of the output** — structured (use code) vs unstructured (use human or LLM judge).

---

### 🔹 Step 5: Run the Model

> **Definition:** Send your entire dataset through the actual system/application and collect its predicted outputs.

**Example:**

| Email | Correct Label | System's Predicted Label |
|-------|----------------|-----------------------------|
| "My card was charged twice" | Billing | Billing ✅ |
| "The app crashes on login" | Technical | General ❌ |
| "What are your hours?" | General | General ✅ |

---

### 🔹 Step 6: Evaluate the Results

> **Definition:** Compare predicted outputs against golden dataset labels and compute the metric defined in Step 2.

```python
# Simple automated accuracy evaluation
def calculate_accuracy(predictions: list, ground_truth: list) -> float:
    """
    predictions   : list of labels predicted by the LLM system
    ground_truth  : list of correct labels from the golden dataset
    Returns accuracy as a percentage
    """
    correct = 0
    total = len(ground_truth)
    
    for pred, actual in zip(predictions, ground_truth):
        if pred == actual:          # compare predicted vs actual label
            correct += 1
    
    accuracy = (correct / total) * 100
    return accuracy

# Example usage
ground_truth = ["Billing", "Technical", "General"]
predictions  = ["Billing", "General",  "General"]

score = calculate_accuracy(predictions, ground_truth)
print(f"Accuracy: {score}%")   # Output: Accuracy: 66.67%
```
