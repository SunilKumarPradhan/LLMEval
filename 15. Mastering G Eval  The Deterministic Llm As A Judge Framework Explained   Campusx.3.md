## ⚙️ The `strict_mode` Parameter {#strict-mode}

> **Definition:** `strict_mode` is a boolean parameter in DeepEval's `GEval` metric that controls **how the final score is computed**.

| Value | Behavior |
|-------|----------|
| `strict_mode=True` | Skips the weighted average calculation. The LLM judge directly outputs a score (e.g., 7 or 8) and that's printed as-is — **binary/direct scoring**. |
| `strict_mode=False` (default, recommended here) | Performs the **full weighted calculation** across all evaluation steps — more nuanced, more reasoned scoring. |

**Why keep it `False`?** Because we *want* the detailed, step-by-step weighted reasoning process (as demonstrated in earlier parts of this series) rather than a blunt direct number. This gives more reliable, explainable scores.

```python
correctness_metric = GEval(
    name="Correctness",
    evaluation_steps=[...],
    evaluation_params=[LLMTestCaseParams.ACTUAL_OUTPUT, LLMTestCaseParams.EXPECTED_OUTPUT],
    strict_mode=False   # False => weighted average calculation (desired behavior)
)
```

## 🔍 Debugging Low Scores — The Golden Dataset Problem {#debugging}

### The Diagnosis Process
The instructor manually read **all 7 failure reasons** and found a **common pattern**:

> **Problem:** The golden dataset's "ideal answers" were written by a human expert to be extremely thorough — covering every angle of a topic. But the RAG pipeline's generated answers, while individually *correct*, often covered only ~70% of the points in the ideal answer.

**Result:** The LLM judge was marking answers as "incorrect" simply because **coverage was incomplete**, not because the content was factually wrong.

> ❓ **Key distinction realized here:** *Correctness* (is the info accurate?) and *Completeness* (does it cover everything?) are **two separate concerns** — but the original evaluation steps were conflating them.

### Example Framing
> If the question is "What is an offline eval?", the golden dataset defines it very thoroughly. If the RAG-generated answer only covers 70% of that definition (but what it says is accurate), the judge was wrongly penalizing it as "incorrect" due to missing coverage — this should instead affect a *Completeness* score, not *Correctness*.

## 🛠️ Refining Evaluation Steps + Adding a Scoring Rubric {#rubric}

### Old Evaluation Steps (Too Strict)
```
1. Compare the actual output against the key facts in the expected output.
2. Heavily penalize statements in the actual output that contradict 
   the expected output and are factually wrong.
3. Reward statements that match the expected output in meaning, 
   regardless of wording.
4. Do not penalize the actual output for omitting information — 
   only wrong statements count here.
```
Even though step 4 *said* "don't penalize for omission," in practice the model was still penalizing incomplete answers — the wording wasn't strict/explicit enough.

### New, Refined Evaluation Steps
```
1. Compare only the factual claims in the actual output against the expected output.
2. A claim is wrong ONLY IF it contradicts the expected output AND is factually false.
3. A factually accurate answer must score at least 9, even if it's shorter, 
   less detailed, and covers fewer points than the expected output — 
   do NOT deduct for brevity.
4. Do not penalize for missing elaboration, fewer examples, or omitted points.
```

### 🆕 Adding a Scoring Rubric (New Concept!)

> **Why add a rubric?** Without one, G-Eval decides *on its own* how to map its reasoning to a numeric score. By providing an explicit rubric, you take that control away from the LLM and make scoring **more deterministic and predictable**.

```python
from deepeval.metrics import GEval
from deepeval.test_case import LLMTestCaseParams
from deepeval.metrics.g_eval import Rubric   # <-- New import required

correctness_metric = GEval(
    name="Correctness",
    evaluation_steps=[
        "Compare only the factual claims in the actual output against the expected output.",
        "A claim is wrong only if it contradicts the expected output and is factually false.",
        "A factually accurate answer must score at least 9 even if it is shorter, "
        "less detailed, and covers fewer points than the expected output. "
        "Do not deduct for brevity.",
        "Do not penalize for missing elaboration, fewer examples, or omitted points."
    ],
    rubric=[
        Rubric(score_range=(0, 4), expected_outcome="Contains a clear factual error."),
        Rubric(score_range=(5, 8), expected_outcome="Mostly correct with minor inaccuracies."),
        Rubric(score_range=(9, 10), expected_outcome="All claims are factually correct."),
    ],
    evaluation_params=[LLMTestCaseParams.ACTUAL_OUTPUT, LLMTestCaseParams.EXPECTED_OUTPUT],
    strict_mode=False
)
```

### Line-by-Line Breakdown

| Line | Explanation |
|------|-------------|
| `from deepeval.metrics.g_eval import Rubric` | Imports the `Rubric` class used to define explicit score bands |
| `evaluation_steps=[...]` | Tells the LLM judge *what aspect* to evaluate (factual accuracy only, ignore length/coverage) |
| `rubric=[Rubric(score_range=(0,4), ...), ...]` | Tells the LLM judge *exactly how to score* — removes ambiguity in the 0-10 mapping |
| `Rubric(score_range=(0,4), expected_outcome="...")` | Defines: if a clear factual error exists → score between 0-4 |
| `Rubric(score_range=(5,8), ...)` | Mostly correct, minor inaccuracies → score 5-8 |
| `Rubric(score_range=(9,10), ...)` | All claims correct → score 9-10 |
| `evaluation_params=[...]` | Specifies which fields of the test case the judge should look at |
| `strict_mode=False` | Keeps the weighted-average calculation (not direct scoring) |
