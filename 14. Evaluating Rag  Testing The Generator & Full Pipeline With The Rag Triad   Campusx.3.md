## <a name="overview"></a>🎯 Overview

This lecture (Part 3) completes the **Generator evaluation** and moves into **full pipeline evaluation** using the concept called the **RAG Triad**. 

**Prerequisites:** You should already know from previous parts:
- What a Retriever is, and how Recall & Precision are calculated for it
- What a Generator is, and how Faithfulness & Answer Relevancy are calculated at the *component level* (using golden context)
- What "LLM as a Judge" and "reference-free evaluation" mean
- What DeepEval is and how golden datasets are structured (`.json` with question, expected/actual output, retrieved context)

**Why this matters:** Individually good components (retriever, generator) don't guarantee a good end-to-end system. This lecture proves — with real numbers — that a retriever can look "great" in isolation but still introduce hidden problems (noise) that only show up when you evaluate the **full pipeline** together. This is a crucial, practical lesson for anyone building production RAG systems.

## <a name="recap"></a>🔁 Recap: The Three Core Components of RAG

> **Definition:** Every RAG system revolves around three core artifacts:
> 1. **Question** — asked by the user
> 2. **Context** — retrieved by the Retriever based on the question
> 3. **Answer** — generated by the Generator using the Question + Context

The entire flow:

```
User Question ──► Retriever ──► Context
                                   │
Question + Context ──► Generator ──► Answer
```

Since there are 3 entities (Question, Context, Answer), there are **3 possible pairwise relationships** — and each relationship has a dedicated metric to measure it.

---

## <a name="rag-triad"></a>🔺 The RAG Triad — Three Metrics Explained

| Relationship | Question Being Asked | Metric Name |
|---|---|---|
| Answer ↔ Context | Is the answer actually derived/grounded in the context? | **Faithfulness** |
| Answer ↔ Question | Is the answer relevant to what was asked? | **Answer Relevancy** |
| Context ↔ Question | Is the retrieved context relevant to the question? | **Contextual Relevancy** |

> **Definition — RAG Triad:** The combination of **Faithfulness**, **Answer Relevancy**, and **Contextual Relevancy** together is called the **RAG Triad**. If a RAG pipeline scores well on all three, it is considered to be working well overall.

This is the **basic fundamental idea** behind evaluating a full RAG system — check all three sides of the "triangle" formed by Question, Context, and Answer.

```
              Question
             /        \
   Answer Relevancy   Contextual Relevancy
           /              \
      Answer ─────────────  Context
           Faithfulness
```

## <a name="component-vs-pipeline"></a>⚖️ Component-Level vs Pipeline-Level Evaluation

A sharp question was raised: *We already calculated Faithfulness and Answer Relevancy while evaluating the Generator (component level). Why calculate them again at the pipeline level? Aren't they the same?*

**Answer: NO — the source of context is different!**

| Aspect | Component-Level (Generator Eval) | Pipeline-Level (Full RAG Eval) |
|---|---|---|
| Context comes from | **Golden dataset** (ideal/reference context, hand-picked) | **Actual Retriever** (real, imperfect retrieval) |
| Purpose | Tests if the Generator can produce good answers *given perfect context* | Tests how the Generator behaves with *real-world, possibly noisy* retrieved context |
| Calculation method | Identical (LLM as a Judge) | Identical (LLM as a Judge) |
| Expected outcome | Often optimistic/idealized scores | Realistic scores reflecting the whole system |

> **Key Insight:** The *formula/method* for calculating Faithfulness and Answer Relevancy is exactly the same in both cases. The **only difference** is: at pipeline level, you swap the "ideal context" with the "retriever's actual context." This one swap can change your scores significantly, because now imperfections in retrieval flow into the Generator's evaluation.

**Practical implication:** If your Generator scored very high (e.g., 92%+) on Faithfulness at component level, but the pipeline-level Faithfulness stays similarly high — that proves your **system prompt for the Generator is robust** even when working with real (possibly imperfect) context.

## <a name="contextual-relevancy"></a>🔍 Contextual Relevancy — Deep Dive

This is the **one metric not yet covered** — it completes the RAG Triad.

> **Definition:** Contextual Relevancy measures **how relevant the context pulled by the retriever is, for answering the question**. It focuses purely on Question ↔ Context relationship (ignores the Answer entirely).

### Step-by-Step Calculation

1. Take a **question**, send it to the **Retriever** (retriever needs nothing else — just the question).
2. Retriever returns `k` contexts (e.g., if `k = 5`, you get 5 chunks of context).
3. Take **each context** and send it to an **LLM-as-a-Judge**, asking it to **break the context down into individual "claims"** (Claim 1, Claim 2, Claim 3, …).
   - Do this for all 5 retrieved contexts.
   - Suppose combined, you get **15 total claims**.
4. For **each of the 15 claims**, individually pair it with the original **question** and ask the LLM Judge: *"Is this claim relevant to answering this question? Yes/No"*
5. Count how many claims got a **"Yes"**. Suppose **10 out of 15** are relevant.
6. **Contextual Relevancy (for that question) = 10 / 15 ≈ 0.67**
7. Repeat this process for all questions in your golden dataset (e.g., 15 questions), then **average** the scores across all questions to get the pipeline's overall Contextual Relevancy.

```
Question ──► Retriever ──► [C1, C2, C3, C4, C5]
                              │
                    Break each Ci into claims
                              │
                    [Claim1, Claim2, ..., Claim15]
                              │
              For each claim: LLM Judge → Relevant? Y/N
                              │
        Contextual Relevancy = (# Relevant Claims) / (Total Claims)
```

> **Note:** This is a **reference-free evaluation** — the golden dataset is used *only* to supply questions. No "ideal answer" or "ideal context" reference is needed for this metric. It's entirely powered by **LLM as a Judge** (or, more expensively, a human evaluator).

## <a name="code-walkthrough"></a>💻 Implementing RAG Triad with DeepEval (Code Walkthrough)

We create a new evaluation file: **`eval_rag_pipeline.py`** inside the `evals` folder (following the same pattern as previous eval files, e.g., `eval_retriever.py`, `eval_generator.py`).

```python
# eval_rag_pipeline.py

# 1. Import the RAG pipeline object we built earlier
from rag_pipeline import rag_pipeline   # your actual pipeline module

# 2. Import DeepEval components
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import FaithfulnessMetric, AnswerRelevancyMetric, ContextualRelevancyMetric

import json

# 3. Load the golden dataset (same dataset used earlier, just questions matter here)
with open("faithfulness_dataset.json", "r") as f:
    golden_dataset = json.load(f)

# 4. Define the model to be used as the "LLM Judge"
model = "gpt-4"          # or whichever model you're using
threshold = 0.5           # pass/fail threshold for each metric

test_cases = []

# 5. For every row in golden dataset, build an LLMTestCase
for row in golden_dataset:
    question = row["question"]

    # 🔑 KEY DIFFERENCE vs component-level generator eval:
    # actual_output now comes from running the FULL PIPELINE (not golden data)
    actual_output = rag_pipeline.generate(question)  

    # 🔑 retrieved_context ALSO comes from the pipeline's retriever,
    # NOT from the golden dataset's "ideal context"
    retrieved_context = rag_pipeline.retrieve(question)

    test_case = LLMTestCase(
        input=question,
        actual_output=actual_output,
        retrieval_context=retrieved_context
    )
    test_cases.append(test_case)

# 6. Define all three RAG Triad metrics (built-in to DeepEval)
faithfulness_metric = FaithfulnessMetric(threshold=threshold, model=model)
answer_relevancy_metric = AnswerRelevancyMetric(threshold=threshold, model=model)
contextual_relevancy_metric = ContextualRelevancyMetric(threshold=threshold, model=model)

# 7. Run evaluation across all test cases and all 3 metrics together
evaluate(
    test_cases=test_cases,
    metrics=[faithfulness_metric, answer_relevancy_metric, contextual_relevancy_metric]
)
```
