## 🎯 Overview

This is **Part 2** of the RAG Operational Evals series. While Part 1 likely introduced *what* operational evals are (Latency, Cost, Throughput, Reliability), this part goes **deep into Latency measurement methodology** and **introduces Cost evaluation**.

> **Operational Evals** measure how well a RAG system performs as an *engineering system* — not how "correct" its answers are (that's Quality Evals), but how **fast**, **reliable**, and **cheap** it is to run in production.

### Prerequisites
- Basic understanding of RAG architecture (Retriever + Generator)
- Familiarity with LLM APIs (OpenAI, Anthropic, Gemini, etc.)
- Basic Python scripting
- Concepts like vector databases, embeddings, re-rankers

### Why This Matters
A RAG system might give perfect answers but if it:
- Takes 10 seconds to respond → users leave (bad UX)
- Costs ₹5 per query → doesn't scale to millions of users (bad economics)

So **before shipping to production**, you must rigorously measure **Latency** and **Cost**, not just "eyeball" them with a single run.

## ⚠️ Why Latency Measurement is Tricky

A naive way to measure latency:

```python
import time

start = time.time()
answer = rag_app.query("What is the capital of France?")
end = time.time()

latency = end - start   # seems simple, right?
```

> **Problem:** This is **NOT reliable**. Why? Because your LLM is an **external API** — its servers may be experiencing load issues, network delays, or throttling at that exact moment ("kuch lafda chal sakta hai server pe"). One single measurement is just **noise**, not signal.

This is why proper operational evaluation follows **4 core rules**, discussed below.

---

## 🔁 Rule 1: Run Multiple Trials & Average

> **Definition:** Instead of sending a question once, send the **same question multiple times** (e.g., 5 times) and average the latency values to cancel out random server noise.

### Why?
- External APIs (OpenAI, Anthropic, Gemini) are **noisy** — network jitter, server load, rate limiting all cause variance.
- A single call could randomly be fast or slow — not representative of "true" performance.

### How it works
If you have **10 questions**, and each is sent **5 times**:

```
Total calls = 10 questions × 5 repeats = 50 latency values
```

You then compute statistics (mean, median, P95, P99) over these 50 values — **not** just one raw number.

**Real-world analogy:** Like measuring your commute time — you wouldn't judge traffic based on one day's drive; you'd average over a week.

---

## 🚨 Rule 2: Track Failures Separately from Latency

> **Definition:** Latency numbers alone can be misleading if you ignore **timeouts/failures**. A system with fewer successful responses can *falsely* appear faster.

### The Trap (Example from Transcript)

| Experiment | Requests Sent | Timeout Rate | P95 Latency | Interpretation |
|---|---|---|---|---|
| Run 1 | 50 | 2% (1 request timed out) | 3.0s | Looks OK |
| Run 2 | 50 | 8% (4 requests timed out) | 2.0s | **Looks "better"** but is actually WORSE |

**Why is Run 2 worse?** Because 8% of requests **never completed** (didn't even count toward latency calc). The system "cherry-picked" only fast successful responses, giving you a **false sense of improvement**.

> ⚠️ **Golden Rule:** Always measure **timeout rate / reliability metrics** *alongside* latency. Never look at latency in isolation.

---

## 🎯 Rule 3: Define Latency Budgets (SLOs)

> **SLO (Service Level Objective):** A self-imposed threshold/"constitution" that defines the maximum acceptable latency — both at the **system level** and **component level**.

### Example Budgets
| Level | Metric | Budget (Threshold) |
|---|---|---|
| System-level | End-to-End P95 Latency | ≤ 3000 ms (3 seconds) |
| Component-level | Retriever latency | ≤ 1000 ms (1 second) |
| Component-level | Time to First Token (TTFT) | ≤ 1200 ms |

### Where does this number come from?
It's a mix of:
- Your **application's nature** (chatbot vs batch report generation)
- **User expectations** (real-time chat needs low latency)
- **Industry standards**

> You must pick ONE number and enforce it as a hard threshold in your eval script — this becomes your **Pass/Fail criterion**.

---

## 🧩 Rule 4: Use Representative & Segmented Workloads

> **Definition:** Your test dataset (the questions you use to measure latency) must reflect the **real diversity** of questions users will ask.

### Why?
If you test **only simple questions**, you'll get an artificially LOW latency number. Once deployed, real users ask complex questions too, and your production latency will be much worse than what you measured.

### Correct Approach — Segment by Difficulty

| Question Type | Count (out of 10) |
|---|---|
| Simple/Easy | 3 |
| Medium | 4 |
| Complex | 3 |

This ensures your latency metrics reflect **real-world usage**, not a best-case scenario.

## 🛠️ Building the Latency Evaluation Script

Instead of a simple "start-stop timer," a **production-grade latency eval script** must incorporate ALL 4 rules above. The instructor built this using an LLM (Claude) with detailed instructions.

### Script Configuration (as described)

```python
"""
eval_latency.py
----------------
Purpose: Measure End-to-End latency, Retrieval latency, 
         Generation latency, and Time-To-First-Token (TTFT)
         for a RAG pipeline, following operational eval best practices.
"""

# --- Configuration ---
NUM_QUESTIONS = 5          # representative & segmented set of questions
REPEATS_PER_QUESTION = 5   # Rule 1: repeat each question multiple times
TOTAL_CALLS = NUM_QUESTIONS * REPEATS_PER_QUESTION  # = 25 calls

WARMUP_RUNS = 2            # first 2 runs (overall, not per question) discarded
                            # to avoid cold-start bias (model loading, cache miss etc.)

# --- SLO / Budget Definitions (Rule 3) ---
SLO_END_TO_END_P95_MS = 3000     # 3 seconds
SLO_TTFT_P95_MS = 1200           # 1.2 seconds
```

### Line-by-Line Explanation

| Line | Explanation |
|---|---|
| `NUM_QUESTIONS = 5` | A small but *segmented* set of questions (simple/medium/complex mix) |
| `REPEATS_PER_QUESTION = 5` | Implements **Rule 1** — repeat each question to average out API noise |
| `TOTAL_CALLS = 25` | Total actual LLM calls made during the experiment |
| `WARMUP_RUNS = 2` | The **first 2 runs overall** (not per-question) are discarded — because the very first calls may involve cold starts (e.g., loading Hugging Face re-ranker models into memory), which artificially inflates latency |
| `SLO_END_TO_END_P95_MS` | The **budget/threshold** — Pass/Fail criterion for the whole pipeline |
| `SLO_TTFT_P95_MS` | The **budget/threshold** for how fast the first token should appear |

> **Correction from transcript:** Initially the instructor said "first 2 runs of *each* question" are discarded — but he corrects himself: it's actually the **first 2 runs of the entire experiment** (out of 25 or 50 total calls) that are discarded as warm-up.

### Running the Script

```bash
python3 -m evals.eval_latency
```

This produces a **detailed report** (discussed below).

> ⏱️ **Note on Scale:** Running only 25 calls is a small sample for a real evaluation. In production, you'd run **500–1000 iterations** to get statistically reliable latency numbers (P95/P99 need large sample sizes to be meaningful).

## 🌊 Streaming & Time-To-First-Token (TTFT)

To measure **TTFT**, the RAG application's generator needs a **streaming feature** — i.e., tokens are streamed to the user as they're generated, rather than waiting for the full response.

> **TTFT (Time To First Token):** The time elapsed between sending a query and the **first token** appearing on the user's screen. This matters for **perceived responsiveness** — even if total generation takes 5 seconds, if the first token appears in 1.5 seconds, the user *feels* like the system is fast.

Without streaming, you can only measure **total generation time** (when the *entire* answer is ready). TTFT requires you to capture the timestamp when the **very first chunk/token** arrives.
