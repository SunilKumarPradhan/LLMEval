## 🎯 Overview

This part of the lecture builds directly on the offline vs. online evaluation distinction and answers the practical question: **"Once my LLM system is deployed, what CAN and CANNOT be measured, and how do I actually build the online evaluation system?"**

**Prerequisites:** Basic understanding of offline evaluation (evaluating with a golden dataset/answer key before deployment), and basic idea of what a RAG chatbot / LLM application is.

**Why this matters:** In real-world production systems (chatbots, AI agents, grading systems), you never have the luxury of a "correct answer key" for live user queries. Companies need a systematic way to catch failures, performance degradation, or quality drops *without* knowing the ground truth in real-time. This is exactly what online evaluation pipelines (logging → signals → dashboards → alerts) solve, and this is a core MLOps/LLMOps skill for building production-grade GenAI systems.

---

## 🔑 Recap: Correctness vs Normality

> **Correctness** = Is the system's output actually *right* (matches what a human/expert would say)?
> **Normality** = Is the system behaving the same way it *usually* does (no sudden abnormal shift)?

- **Offline evaluation** → measures **correctness** (you have a golden dataset with human-labeled answers to compare against).
- **Online evaluation** → mostly measures **normality**, not correctness, because production doesn't have ground-truth answers for every live query.

---

## ❓ Why Correctness Can't Be Measured Online

**Scenario:** You built an automated exam-paper grading system (like a UPSC answer evaluator).

1. Offline: You tested it against a set of papers with known human-given marks. Satisfied → Deployed.
2. Online (in production): A new paper comes in. Can you check if the system graded it *correctly*?

**Answer: NO.** Because:
- The current answer being evaluated has **no human-assigned score** to compare with.
- There is **no golden dataset entry** for this specific new answer.
- The human perspective is missing entirely in production — this is the **first time** ever this particular answer is being judged.

> **Core insight:** *Once deployed, you lose your reference/ground truth for brand-new inputs. So correctness cannot be directly measured online — but you CAN check if the system is behaving normally.*

## 📊 The Distribution Comparison Technique

Since correctness can't be verified live, we use a smart workaround: **compare score distributions over time**.

**Example (Exam Grading System):**
- Week 1 (Baseline): 1000 students' papers evaluated.
  - Most students score around 500
  - Many around 700
  - Few around 200
- This becomes your **baseline distribution**.
- Weeks 2, 3, 4: Distribution stays roughly the same → system considered "behaving normally."
- **Week 5 (Anomaly):** Suddenly most students score around 800, very few around 200-500.

```
Baseline Distribution (Normal)        Week 5 Distribution (Abnormal)
     ▲                                      ▲
     |      ▄▄▄                             |            ▄▄▄
     |    ▄█████▄                           |          ▄███████▄
     |  ▄████████▄▄                         |        ▄███████████▄
     |▄███████████████▄                     |    ▄▄▄████████████████▄
     +--------------------► Score           +--------------------► Score
      200   500    700   1000                200   500    700   1000
```

**What this tells us:**
- Something changed — **but we don't know if it's good or bad automatically**.
- It could genuinely be a smarter batch of students, OR it could be a bug in the grading logic.
- This distribution shift gives you a **trigger** to go investigate — it doesn't confirm correctness, it flags **abnormality**.

> **Definition:** *This comparison against a rolling baseline distribution is the essence of online evaluation — it tells you "something is different," prompting investigation, rather than confirming "this specific answer is right."*

## 🔄 Alternative Signals for Correctness

Since direct correctness isn't always measurable online, we use **proxy signals** depending on the type of metric:

### Case 1: Metrics that DON'T need a correct answer
Example: **Faithfulness** in a RAG chatbot.

> **Faithfulness** = Was the generated answer actually derived from the retrieved context (not hallucinated)?

- You already have: the **retrieved context** + the **generated answer**.
- You can ask an LLM: *"Is this answer grounded in this context?"* — **No need for a pre-known correct answer.**
- Such metrics can be computed directly online.

### Case 2: Metrics that DO need a correct answer (Correctness itself)
Example: A general-purpose chatbot answering arbitrary user questions.

**Problem:** User can ask *anything*. You have no answer key for arbitrary questions. So how do you know if answers are correct?

**Solution — Jugaad (workaround) signals:**
1. **Distribution comparison** (as discussed above) — for structured tasks like grading.
2. **User feedback signals** — e.g., **Thumbs Up / Thumbs Down**.
   - If thumbs-down ratings spike suddenly in the last hour → strong signal something is wrong.
   - This becomes a **substitute/proxy for correctness** when ground truth is unavailable.

| Situation | Approach |
|---|---|
| Metric doesn't need correct answer (e.g., faithfulness, toxicity) | Compute directly via LLM evaluator |
| Metric needs correct answer but none available (e.g., correctness of open-ended chatbot) | Use proxy signals: distribution shifts, user feedback (thumbs up/down), escalations |

## 1️⃣ Step 1: Logging

> **Definition:** *Logging is the process of capturing a structured, replayable record of every conversation turn happening in production, so nothing is lost and everything can be evaluated/audited later.*

**Why it's needed:** If you don't record live conversations, they're gone forever, and there's nothing left to evaluate.

### 📦 What Gets Logged
For every conversation happening on your deployed chatbot (e.g., 50,000 conversations/day on CampusX's chatbot):

| Data Type | Examples |
|---|---|
| **Identifiers** | Conversation ID, Turn ID, User ID, Session ID |
| **Timing** | Timestamp of each turn |
| **Content** | User's question, retrieved context (for RAG), model's generated output |
| **Operational metrics** | Latency (ms), prompt tokens, completion tokens, total cost, errors/status codes |
| **Behavioral signals** | Thumbs up/down, escalation requests (e.g., "talk to a human"/"email me"), repeated/rephrased questions (frustration signal) |

### ⚙️ Engineering Properties of Logging

| Property | Meaning | Why It Matters |
|---|---|---|
| **Non-blocking** | Logging must run in parallel, not interfere with the chat operation | Logging + chatting together should NOT increase user-facing latency |
| **Durable & Queryable** | Data stored in a structured way (data warehouse / observability tool like LangSmith) | You must be able to fetch/query this data anytime in the future |
| **Late Signal Attachment** | Some signals (e.g., escalation via email a day later) arrive *after* the conversation ends | Must still be linked back to the original Conversation ID for accurate tracking |
| **PII Handling / Masking** | Mask/remove sensitive personal info (phone number, card number, address, Aadhar number) before storing | Prevents privacy leaks; teammates/employees shouldn't extract sensitive data later |

> **PII** = Personally Identifiable Information (phone number, card number, DOB, Aadhar number, etc.)

### 🛠️ Tool Example: LangSmith
- LangSmith is an **observability tool** used to log and store every conversation of an LLM-based application.
- Inside LangSmith, you organize logs by **Projects**.
- Each project shows all conversations (traces) with full metadata: user input, model output, tokens, cost, latency, errors, etc.

## 2️⃣ Step 2: Types of Signals — Captured vs Computed

Once conversations are logged, we need to decide *what to track*. There are **two categories of signals**:

### 🟢 Captured Signals
> **Definition:** *Signals that already exist as-is in the data — you just store them directly, no calculation needed.*

**Examples:**
| Signal | Description |
|---|---|
| Thumbs Up/Down | User directly gives this feedback — store as-is |
| Latency | Time taken by chatbot to respond — measured directly |
| Cost per conversation | Tokens × price — usually pre-calculated by LLM provider |
| Token usage | Simple counting — no real-time computation needed |

> No real-time calculation required — you just capture and store.
