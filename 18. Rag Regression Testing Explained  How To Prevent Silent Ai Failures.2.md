## 1. Overview {#overview}

> **What this session covers:** How to actually *execute* a RAG regression testing pipeline end-to-end — from running baseline evaluations, making a code change, regenerating candidate results, comparing both, and finally deciding (programmatically + humanly) whether to ship the change or block it.

**Prerequisites:**
- Understanding of RAG pipeline components (Retriever, Generator, full Pipeline, Application layer)
- Familiarity with the 14 evaluation metrics already built in Part 1 (Quality, Safety, Operational metrics)
- Basic Python scripting knowledge
- Concept of baseline vs candidate comparison (regression testing fundamentals)

**Why it matters:**
In real production RAG systems (think ChatGPT-scale), even a "small improvement" (like reducing chunk size to boost contextual relevance) can silently break something else — safety, PII leakage, etc. Without a structured regression testing pipeline, these silent failures ship to production undetected. This session shows how to **operationalize** regression testing into a repeatable, automatable workflow — this is essentially "CI for RAG" done manually in code, before plugging into GitHub Actions or an MLOps tool.

## 2. Recap: Why Regression Testing Exists {#recap}

> **Regression Testing (in RAG context):** The process of verifying that a change (config change, prompt change, model change, chunking strategy change, etc.) does not silently degrade previously working behavior — measured via a fixed set of quality, safety, and operational metrics compared against a stored baseline.

Two core problems this pipeline solves:
1. **Direction ambiguity** — For a given metric, does "higher" or "lower" mean better? (e.g., latency lower = better, recall higher = better)
2. **Noise vs real signal** — Small fluctuations happen naturally between runs (LLM non-determinism, sampling variance). How do we know if a metric change is a *real regression* or just *noise*?

Both problems are solved using a **Metric Registry** (direction + noise threshold) combined with **repeated baseline runs** (to measure natural variance).

### 3.1 `run_suite.py` — The Orchestrator 🎬

> **Definition:** The main pipeline file that runs ALL evaluation scripts (quality, safety, operational) in sequence and logs the aggregated results into a JSON file.

**What it does, step by step:**
1. Runs all **Quality Evals** (Retriever eval, Generator eval, Pipeline eval, Application eval)
2. Runs all **Safety Evals**
3. Runs all **Operational Evals** (latency, cost, reliability)
4. Generates a complete report of "what's happening" across all 14 metrics
5. **First run** → stores results in `baseline.json`
6. **Every subsequent run** → stores results in `candidate.json`

```python
# run_suite.py (conceptual structure)

import json
from evals.retriever_eval import run_retriever_eval
from evals.generator_eval import run_generator_eval
from evals.pipeline_eval import run_pipeline_eval
from evals.application_eval import run_application_eval
from evals.safety_eval import run_safety_eval
from evals.operational_eval import run_operational_eval
import os

def run_suite(note: str = ""):
    """
    Orchestrates all 6 evaluation categories and stores results
    either as baseline.json (first run) or candidate.json (subsequent runs).
    """
    results = {}

    # 1. Quality Evals (4 sub-categories)
    results["retriever"] = run_retriever_eval()      # recall, precision, contextual relevance
    results["generator"] = run_generator_eval()       # faithfulness, answer relevance
    results["pipeline"] = run_pipeline_eval()          # end-to-end correctness metrics
    results["application"] = run_application_eval()    # UX/application-level metrics

    # 2. Safety Evals
    results["safety"] = run_safety_eval()              # toxicity, PII leakage, bias, etc.

    # 3. Operational Evals
    results["operational"] = run_operational_eval()    # latency, cost, reliability

    results["note"] = note  # log the change description (e.g. "chunk size reduced")

    # Decide where to save
    if not os.path.exists("baseline.json"):
        output_file = "baseline.json"
    else:
        output_file = "candidate.json"

    with open(output_file, "w") as f:
        json.dump(results, f, indent=2)

    print(f"Results saved to {output_file}")

if __name__ == "__main__":
    note = input("Describe the change you made: ")
    run_suite(note)
```

**Line-by-line breakdown:**
| Line | Explanation |
|------|-------------|
| `import json` | To serialize eval results into a `.json` file |
| `run_retriever_eval()` etc. | Each function encapsulates one eval category built in previous sessions |
| `results["note"] = note` | Logs a human-readable description of what changed (helps in audit trail) |
| `if not os.path.exists("baseline.json")` | Ensures the *first ever run* becomes the ground truth baseline |
| `else: output_file = "candidate.json"` | All later runs (after changes) are treated as "candidates" to be compared |
| `json.dump(results, f, indent=2)` | Pretty-prints JSON for human readability |

**Why this design?** So that the developer doesn't have to run 6 separate scripts manually every time — one command (`run_suite.py`) triggers everything "behind the scenes."
