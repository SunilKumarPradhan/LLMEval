## <a name="overview"></a>🎯 Overview

This is **Part 3** of the RAG Operational Evals series. By this point, **Latency evaluation** has already been covered in detail (Part 1/2). This part completes the **Operational Evals** trio by covering:

1. **Cost Evals** — How much money does each query cost, and how to reduce it?
2. **Reliability Evals** — How often does the system successfully serve a request without crashing/erroring/timing out?
3. **Throughput** (briefly mentioned, not implemented — needs dedicated load-testing tools)

> **Operational Evals** are different from **Quality Evals** (which use golden datasets + LLM-as-a-judge). Operational Evals measure the *system's operational health* — speed, cost, and reliability — NOT whether the answer is "correct". Importantly, **no LLM-as-a-judge is used** in any of these operational eval scripts — they're purely based on system telemetry (tokens, timers, success/failure flags).

**Prerequisites:** Understanding of basic RAG pipeline (retriever, reranker, LLM generation), Python, and OpenAI API basics. Familiarity with Latency Evals (Part 1/2) is assumed.

**Why this matters:** In production, a RAG system that gives perfect answers but costs too much, is too slow, or fails frequently is *not shippable*. These three metrics decide whether your system passes its **SLO (Service Level Objective)** before going live.

## <a name="cost-eval"></a>💰 Cost Evaluation

### 🔹 What is Cost Eval & Why It Matters

> **Definition:** Cost Eval measures how much money (in USD/INR) it takes, on average, to answer one query through your RAG pipeline — accounting for input tokens, output tokens, and current model pricing.

**Why it's needed:**
- Every LLM call has a $ cost based on input + output tokens.
- At scale (thousands of queries/day), even small per-query costs add up to significant monthly bills.
- Unlike latency, **cost is a much more stable/reliable metric** — it doesn't fluctuate much because pricing rates are fixed. Latency varies a lot (network, server load, etc.), but cost barely does — since you're always being charged the same rate per token.

**Where to measure:** Cost can be reliably measured **either post-deployment or offline (on your laptop)** — unlike latency, which needs real deployment conditions to be meaningful. This is because token pricing is fixed regardless of environment.

```python
# eval_cost.py — Conceptual reconstruction based on transcript description

import time
from openai import OpenAI

client = OpenAI()

# ---- CONFIGURATION ----
MODEL_NAME = "gpt-4o-mini"          # same model used by the actual RAG chatbot
INPUT_PRICE_PER_1M = 0.15           # $ per 1M input tokens (example rate for gpt-4o-mini)
OUTPUT_PRICE_PER_1M = 0.60          # $ per 1M output tokens
USD_TO_INR = 95.0                   # corrected conversion factor (was wrongly 88 earlier)

DAILY_QUERY_VOLUME = 2000           # projection: how many queries/day expected in production

# Sample test questions (representative of real usage, not a golden dataset)
test_questions = [
    "What is the refund policy?",
    "How do I reset my password?",
    "What are the shipping charges?",
    "Can I cancel my subscription anytime?",
]

REPEATS_PER_QUESTION = 3  # send each question 3 times to see cost variance

def get_cost_for_query(question: str):
    """
    Sends a query through the RAG pipeline (LLM call) and computes
    the exact cost based on token usage returned by the API.
    """
    start = time.time()
    response = client.chat.completions.create(
        model=MODEL_NAME,
        messages=[
            {"role": "system", "content": "You are a helpful RAG assistant..."},
            {"role": "user", "content": question}
        ]
    )
    usage = response.usage  # contains prompt_tokens, completion_tokens, cached_tokens

    input_tokens = usage.prompt_tokens
    output_tokens = usage.completion_tokens

    input_cost = (input_tokens / 1_000_000) * INPUT_PRICE_PER_1M
    output_cost = (output_tokens / 1_000_000) * OUTPUT_PRICE_PER_1M
    total_cost = input_cost + output_cost

    return {
        "question": question,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "cost_usd": total_cost
    }

def run_cost_eval():
    results = []
    for q in test_questions:
        for _ in range(REPEATS_PER_QUESTION):
            results.append(get_cost_for_query(q))

    total_cost = sum(r["cost_usd"] for r in results)
    avg_cost = total_cost / len(results)

    print(f"Total samples run: {len(results)}")
    print(f"Average cost per query: ${avg_cost:.6f} (~₹{avg_cost * USD_TO_INR:.4f})")
    print(f"Min cost: ${min(r['cost_usd'] for r in results):.6f}")
    print(f"Max cost: ${max(r['cost_usd'] for r in results):.6f}")

    # ---- PROJECTIONS ----
    daily_cost_usd = avg_cost * DAILY_QUERY_VOLUME
    monthly_cost_usd = daily_cost_usd * 30
    print(f"Projected daily cost ({DAILY_QUERY_VOLUME} queries/day): ₹{daily_cost_usd * USD_TO_INR:.2f}")
    print(f"Projected monthly cost: ₹{monthly_cost_usd * USD_TO_INR:.2f}")

if __name__ == "__main__":
    run_cost_eval()
```

**Line-by-line explanation:**

| Code Part | Purpose |
|---|---|
| `MODEL_NAME = "gpt-4o-mini"` | Same model used by the actual chatbot AND the eval — important to avoid confusion (no separate "judge model" needed here since there's no judging happening) |
| `INPUT_PRICE_PER_1M`, `OUTPUT_PRICE_PER_1M` | Hardcoded because pricing is known per model (from provider's pricing page) |
| `USD_TO_INR` | Currency conversion — must be kept updated manually |
| `test_questions` + `REPEATS_PER_QUESTION` | 4 questions × 3 repeats = 12 samples — enough to see cost stability, not a golden dataset |
| `response.usage` | OpenAI API returns exact token counts used — this is the ground truth for cost calculation |
| `input_cost`, `output_cost` | Straightforward token-count × rate math |
| Projections section | Extrapolates per-query average cost to daily/monthly volume — critical for budgeting |
