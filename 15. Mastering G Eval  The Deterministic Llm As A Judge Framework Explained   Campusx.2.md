## 🎯 Overview

This section dives deep into **G-Eval**, a technique that fixes the biggest flaw of "LLM-as-a-Judge" evaluation — **inconsistency (variance) across evaluation runs**.

**Prerequisites:**
- Basic understanding of LLM-as-a-Judge technique
- Familiarity with RAG pipelines (question → context → answer)
- Basic idea of what "evaluation metrics" mean (precision, recall, etc.)
- Basic Python and DeepEval library exposure

**Why this matters:**
- Many quality aspects of an LLM response (correctness, completeness, style, helpfulness, safety) **cannot be measured by counting words** — they need *judgment*.
- Plain "LLM-as-a-Judge" (ask the LLM to output a score 0-10) is **unreliable** — the same prompt run twice can give wildly different scores (e.g., 6 vs 8).
- G-Eval makes this judging process **deterministic and stable** using two innovations: (1) Chain-of-Thought based evaluation steps, and (2) probability-weighted scoring using log probabilities instead of raw token output.

## 🔁 Recap: The Problem with LLM-as-a-Judge

> **LLM-as-a-Judge**: A technique where instead of counting overlapping words/n-grams, you ask an LLM to *judge* whether a response meets some criteria (e.g., correctness, helpfulness) and output a score.

**The Big Flaw:**
- You ask the LLM: *"Give a score from 0 to 10."*
- The LLM outputs a **single integer** — could be 6, 7, or 8 depending on the run.
- Because this integer is directly sampled/generated, there's **high variance** between runs — the same input can yield different scores each time you call the API.

**Two root causes of this variance:**
1. You give the LLM a **high-level criteria** only (e.g., "check factual correctness") and let it figure out the reasoning steps on its own — every run it might "think" a bit differently.
2. You take the **literal output token** (e.g., "8") as the final score — a single sampled token is inherently noisy.

G-Eval solves **both** of these problems.

## 🤖 How LLMs Generate Output (Autoregressive Behavior)

To understand G-Eval's second innovation, you must understand how any LLM/Transformer generates text.

**Key Mechanics:**
- The final layer of a language model network has **as many nodes as there are output tokens** in its vocabulary (e.g., 10,000 tokens — covering all words, digits, punctuation, etc.)
- For a given input, the model assigns a **probability to every single token** in its vocabulary.
- The token with the **highest probability** gets printed as output in that generation step.
- That printed token is then **appended back to the input**, and the whole process repeats to generate the next token.

> **Definition — Autoregressive Manner**: The process where an LLM generates output one token at a time, each time feeding its own previous output back as input to predict the next token.

**Example:**
- Tokens like "is", "the", "0", "hello" etc. all get probabilities assigned.
- Say "is" → 61%, "the" → 31%, etc.
- Whichever token has the **max probability** gets printed → becomes part of input → cycle repeats.

## ❓ The Core Problem with Direct Score Extraction

When your prompt says: *"Analyze this and give a score from 0 to 10"*:

- Out of the 10,000 possible output tokens, **naturally the tokens 0–10 will get the highest probabilities** (since the prompt explicitly restricts the expected output format).
- All other tokens (words like "is", "the") get very low probabilities — because they can never be valid output for this prompt.

**Normal (non-G-Eval) behavior:**
- The system just picks the token with the **single highest probability** (e.g., "8") and prints it as the final score.
- This ignores how confident the model was about other close contenders (like 7 or 9).
- This is why running the same evaluation twice can jump from 6 to 8 — a small shift in internal probability can flip which single token wins.

---

## 💡 G-Eval's Solution: Probability-Weighted Scoring

> **G-Eval's core idea**: Instead of taking the LLM's single output token as the score, extract the **probabilities of the top-K candidate tokens**, normalize them, and compute a **weighted average** — this becomes the final score.

**Why this works:**
- It factors in **how confident** the model was about 7, 8, AND 9 — not just the winning token (8).
- This produces a **smoother, more stable number** because it's an average across multiple possibilities, not a single sampled token.
- Because we're averaging, the score naturally resists large jumps between runs (e.g., it might move from 7.84 → 7.4 or 7.9, but won't jump wildly like 6 → 8).

## 🧮 Step-by-Step Weighted Score Calculation

Let's walk through the exact numeric example from the transcript.

### Step 1: Extract Top-K Token Probabilities
LLMs typically allow you to extract only the **top-K token probabilities** (not all 10,000 — too much compute). Let's say K = 5.

Example top-5 tokens and their raw probabilities for a given prompt:

| Token | Probability |
|-------|-------------|
| 8 | 0.70 |
| 7 | 0.20 |
| 9 | 0.05 |
| "the" | 0.01 |
| ":" | (small) |

### Step 2: Discard Non-Numerical Tokens
Since the prompt asks for a numeric score, non-numerical tokens like "the" and ":" are **irrelevant and discarded**.

Remaining:
| Token | Probability |
|-------|-------------|
| 8 | 0.70 |
| 7 | 0.20 |
| 9 | 0.05 |

### Step 3: Normalize the Remaining Probabilities
Sum = 0.70 + 0.20 + 0.05 = **0.95** (not 1, since we dropped some tokens)

Normalize by dividing each by 0.95:

| Token | Normalized Probability |
|-------|------------------------|
| 8 | 0.70 / 0.95 ≈ **0.73** |
| 7 | 0.20 / 0.95 ≈ **0.21** |
| 9 | 0.05 / 0.95 ≈ **0.053** |

### Step 4: Compute Weighted Average
```
Weighted Score = (8 × 0.73) + (7 × 0.21) + (9 × 0.053)
              ≈ 5.84 + 1.47 + 0.48
              ≈ 7.84
```

### Step 5: Compare to Normal (Non-G-Eval) Output
If you had just taken the single highest-probability token directly, output would simply be **"8"** (since 8 has the max probability, 70%).

> G-Eval instead gives **7.84** — a more nuanced, stable score that reflects overall model confidence, not just the top pick.

### Step 6: Normalize to 0–1 Range
Divide the weighted score by 10 (since final scores must be in the 0-1 range):
```
7.84 / 10 = 0.784
```

### Step 7: Apply Threshold
Compare against a threshold (commonly **0.7**):
- If score ≥ threshold → **Pass** (answer is correct)
- If score < threshold → **Fail** (answer is incorrect)

Since 0.784 > 0.7 → **Pass**.

### Paper Example (mentioned in transcript)
The original G-Eval paper illustrates this with token "1", "2", "3":
- Normal token extraction → output would be "3"
- G-Eval weighted approach → output is **2.59**

This shows the score is "pulled" toward a more stable, blended value rather than jumping to a single integer.

## 🚀 The Two Core Innovations of G-Eval

G-Eval is essentially **LLM-as-a-Judge + 2 clever fixes**. Nothing more, nothing less.

### Innovation 1: Chain-of-Thought (CoT) Based Evaluation Steps

> Instead of sending a single high-level criteria to the LLM judge, G-Eval first uses CoT to **break down that criteria into detailed evaluation steps** (a full "rulebook"), and sends that complete rulebook with every API call.

**Why this helps:**
- Every API call now gives the LLM **more clarity** about exactly what to do.
- Less room for the LLM to "think differently" each time → **less variance**.
- More deterministic, repeatable behavior.

**Analogy**: Instead of telling an exam evaluator "grade this fairly," you give them a **detailed marking rubric** — they'll be much more consistent across different answer sheets.

### Innovation 2: Log Probability–Weighted Scoring (instead of direct token extraction)

> Rather than extracting the literal token value the LLM outputs (e.g., "8"), G-Eval extracts the **log probabilities of the top-K candidate tokens**, normalizes them, and computes a **weighted average** as the final score.

**Why this helps:**
- Produces **stable, reliable scores** across multiple evaluation runs.
- Captures the model's underlying confidence distribution instead of a single noisy sample.

**Combined Effect:**
Together, these two innovations make G-Eval **more deterministic** than plain LLM-as-a-Judge, which is why it consistently **beats other evaluation metrics** in benchmark comparisons (as shown in the original G-Eval paper).

> 🗣️ *"G-Eval is not something entirely new — it's still LLM-as-a-Judge. It just has two core innovations that make it better."*
